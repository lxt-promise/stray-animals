# 特征库自动建库（A + B + C 方案）

> 目标：**新猫建档后，管理员不必记得去点「建库」，AI 也能认得它。**

---

## 一、为什么需要这几条自动路径

识别链路是：

```
云函数 → POST /v1/recognize（含本校 cats 列表）→ 自建识别服务
                                                  ├─ ensure_index(cats)  ← 冷启动补库
                                                  └─ search(query, cats)
```

`search()` **只在服务端本地特征库里检索**，请求里的 `cats` 仅用于把向量 id 回表补成
name/avatar。而 `ensure_index()` 的入参判断是：

```python
if not c.photos or index_store.get(c.id) is not None:
    continue          # 没照片 → 直接跳过
```

早前为了让单次识别压进客户端约 3 秒的 `callFunction` 预算，识别报文做了瘦身，
**不再携带档案照**（带上会让服务端疯狂下载，把调用拖爆）。
代价就是：**`ensure_index` 没了素材，新建档的猫不会自动进特征库**。

于是补两条自动路径：

| 方案 | 触发时机 | 作用 | 覆盖场景 |
|---|---|---|---|
| **C 建档即入库** | 保存档案那一刻 | 只把**这一只**猫送进服务端特征库 | 建档后**立即**可被匹配 |
| **A 增量补库** | 每次识别（热路径） | 只给「未入库」的猫带照片（限量），服务端在检索前补算 | C 没跑成时的**即时补救** |
| **B 定时全量** | 每天凌晨 3:00（定时触发器） | 遍历所有校区，只补缺失的 | 批量建档、服务曾不可用时的**兜底** |

三条路径互相兜底，任意一条成功即可；全部失败也只是退化成「靠花色 + 位置猜」，
**绝不会让建档或识别报错**。

## 二、C 方案：建档 / 改档后自动入库

### 为什么单独拆一次调用

建档本身已经包含**文字安全检测 + 图片安全检测 + 落库**，再叠上建库（服务端要下载
并编码照片）必然顶爆客户端约 3 秒的 `callFunction` 预算。所以不在 `saveCat` 里同步等，
而是**保存成功后由前端再发一次独立调用** —— 两次调用各有各的 3 秒预算。

```
管理员点保存
   └─ callApi('saveCat')            ← 预算 3s：安全检测 + 落库（aiIndexAt 置空）
        └─ callApi('autoIndexCat')  ← 预算 3s：只带这 1 只猫的照片 → /v1/index/build
                                        └─ 成功 → 写回 aiIndexAt，toast「已加入比对」
                                        └─ 失败/超时 → 静默，交给 A / B
```

### 接口

`autoIndexCat`（role = **admin**，与 `saveCat` 对齐）

| 入参 | 默认 | 说明 |
|---|---|---|
| `catIds` | 必填 | 最多取前 3 个，建档场景只传 1 个 |
| `schoolId` | 空 → 回落到当前用户所属学校 | |
| `photosPerCat` | 2（上限 3） | 只取前几张，够算代表向量即可 |
| `timeoutMs` | 2000（区间 800–2200） | 硬压在 2.2s 内，给客户端留收尾时间 |

返回值：`{ ok, schoolId, scanned, built, failed, skipped, indexed }`；
失败时 `{ ok:false, deferred:true, msg }` —— **永不抛错**。

### 与 A 的分工

`buildIndex` 现在支持 `catIds` 过滤：传了就 `where({_id: _.in(catIds)})`，
只换这几只猫的临时链接；不传才是全校扫描（定时任务 / 手动全量走的宽路）。

| | C | A |
|---|---|---|
| 换临时链接的数量 | 1 只猫 × ≤3 张 | ≤6 只猫 × ≤2 张 |
| 时机 | 建档那一刻 | 第一次有人识别 |
| 位置 | 前端二次调用 | 识别热路径内联 |

## 三、A 方案：识别热路径增量补库

### 记账字段

猫档案新增一个普通字段 **`aiIndexAt`**（最后一次送服务端入库的时间）：

- 建档 / 改档时置空 → 表示「需要入库」（见 `index.js` 的 `saveCat`）；
- 识别成功携带照片后批量写回 → 表示「已入库」，下轮不再重复携带。

只加字段，**不新增集合**。

### 流程

```
识别 step 'cats'
  └─ loadCatsLite()            轻量读档案（含 aiIndexAt）
  └─ attachPendingPhotos()     挑出 !aiIndexAt 且有照片的猫，限量 ≤ 6 只
                               → 换临时链接（一次批量 getTempFileURL）
                               → 预算不足 / 换取失败 → 静默跳过，识别照常
  └─ 调 /v1/recognize，报文里只有这几只猫带 photos
  └─ 服务端 ensure_index 补算 → search 立即可命中
  └─ 成功后 markIndexed(ids)   一次批量 update 记账（不 await）
```

### 三条硬约束（踩过的坑）

1. **必须限量**：`PENDING_INDEX_MAX = 6`。一次带 200 只猫的照片会让服务端下载到天荒地老，
   必然越过 3s 预算 —— 这正是当初「27 轮轮询全超时」事故的病根。
   超量的猫由定时任务分片补齐（渐进收敛）。
2. **记账必须批量**：一次 `where({_id: _.in(ids)}).update()`。
   逐只 `doc().update()` 会按猫数放大 DB 往返，直接顶穿「单次 poll 往返 ≤ 7」的红线。
3. **不写 `updatedAt`**：那是档案的业务字段，不该被记账动作污染。

## 四、B 方案：每天定时全量建库

### 接线

`cloudfunctions/catcampus/config.json` 里声明定时触发器：

```json
{
  "triggers": [
    { "name": "aiIndexDaily", "type": "timer", "config": "0 0 3 * * * *" }
  ]
}
```

七位 cron：`秒 分 时 日 月 星期 年` → 每天 03:00。
**上传部署云函数后触发器才会生效**（开发者工具：右键云函数 → 上传并部署）。

### 定时分支的安全设计

定时触发器由平台构造 event：`{ Type: 'Timer', TriggerName, Time }`，
**没有 OPENID**，`getMe()` 必然返回 null，走 `requireRole` 只会 401。
所以 `index.js` 里它是独立分支，遵循两条规矩：

1. **白名单制**：只放行表内 `TriggerName`，未知的直接 404 ——
   防止有人手工塞一个 `Type:'Timer'` 的 event 来触发管理端动作。
2. **系统身份**：直接用 admin 语义执行；且定时任务天然是系统调度，无需再校验。

### 分片推进

一个校区几百只猫要换成百上千个临时链接，服务端还要逐张下载编码，
一次性做完必然越过云函数超时。所以：

- 带**总 deadline**（默认 15s，环境变量 `AI_INDEX_TIME_BUDGET_MS` 可调）；
- 校区之间检查剩余时间，**预留 1.5s 收尾**；
- 把**本次剩余预算**直接传给建库请求（`timeoutMs`），尽量一次多建几只；
- 单校失败不影响其他校区（逐校 `try/catch`）；
- 返回 `timedOut` 与 `pendingSchools`，供运维判断是否要加大预算。

### 幂等是收敛的前提

定时任务一律带 `onlyMissing: true`：服务端已有向量的猫**连照片都不下载**，
直接跳过。所以每天跑一次的成本 ≈ 只建当天新增的猫。

需要整体重建时（改名 / 换照片 / 清库后）显式传 `force: true`。

## 五、部署清单

1. **上传部署云函数 `catcampus`** —— 本次改动涉及 `lib/vision.js`、`index.js`。
2. **确认 `config.json` 一并上传**，定时触发器才会创建。
3. 环境变量（云函数配置面板）：
   | 变量 | 默认值 | 说明 |
   |---|---|---|
   | `AI_ENDPOINT` | 无 | 必须为 `.../v1/recognize` 结尾，才能推导建库地址 |
   | `AI_TOKEN` | 无 | 与识别服务的 `API_TOKEN` 一致 |
   | `AI_INDEX_TIME_BUDGET_MS` | 15000 | 定时任务总预算，需小于云函数超时 |
   | `AI_INDEX_TIMEOUT_MS` | 20000 | 单个建库请求超时 |
4. **云函数超时**：默认常见 20s。若要一次建更多校区，调到 60s 并把
   `AI_INDEX_TIME_BUDGET_MS` 提到 45000 左右。
5. **重新编译小程序**。

## 六、上线后用户上传新猫会怎样

**普通用户打卡时没选猫** → 落的是 pending 待认领记录，**不会创建猫档案**，
不参与 AI 匹配。打卡照常记录、猫粮值照常发 —— 这条路径完全不受影响。

**管理员核实后建档** → 猫进入档案库：

- 属性兜底匹配**立即生效**；
- 特征比对在**保存档案那一刻就自动入库**（C 方案），成功会 toast「已加入比对」；
- 万一 C 没跑成，下一次有人识别时自动补（A 方案），最迟次日凌晨补齐（B 方案）。

即使两条路径都没跑（比如识别服务完全不可用），识别也**不会报错**，只是退化成
「靠花色 + 位置猜」。

## 七、运维自查

```bash
curl https://<你的识别服务域名>/health
```

关注返回里的：

- `"provider"`：应为 `onnx`（占位引擎的话结果是稳定但无意义的）；
- `"ffmpeg"`：视频真抽帧需要，应为 `true`；
- `"indexed"`：特征库里的猫数。长期为 0 说明从没建成功过。

### 特征库到底存在哪

**不在小程序的云开发数据库里。** 两套存储各管一摊：

| 存储 | 位置 | 存什么 |
|---|---|---|
| 云开发数据库 `cats` 集合 | 微信云开发 | 猫档案业务字段，**外加一个 `aiIndexAt` 时间戳（记账标记）** |
| 自建识别服务的特征库 | `server/`，后端由 `INDEX_BACKEND` 选择（见下） | **真正的特征向量**（每只猫一条，float32 二进制） |

向量不进向量数据库：几百只猫 × 每条几 KB，全表才几 MB，
全量载入内存做矩阵乘比接一套向量库划算得多。

**两种存储后端**（`server/app/index_store.py` 是门面，六方法契约不变）：

| `INDEX_BACKEND` | 载体 | 适用 |
|---|---|---|
| `sqlite`（默认） | 本地文件 `INDEX_DB`（默认 `/data/catcampus/index.sqlite3`），表 `cat_index(cat_id, school_id, dim, embedding, source, updated_at)` | 本机开发；**部署在云托管时实例回收即丢库** |
| `cos` | 对象存储，**每猫一对象** `index/<cat_id>.bin`（自描述头 dim + school_id + float32 向量） | 云托管生产；新增=PUT / 删除=DELETE，天然原子，实例缩容到 0 也不丢 |

配了 `cos` 后 `/health` 会多返回 `indexBackend` 字段（值为 `cos_store` 或 `sqlite_store`），
用它一眼确认到底切没切过去 —— 别把「以为在用 COS」当成在用 COS。

⚠️ **持久化**：sqlite 后端部署在会缩容到 0 的云托管上，必须给 `INDEX_DB` 所在路径挂
**持久化存储**（CFS/NAS），否则实例回收后特征库丢失 —— 这正是 B 方案（每晚全量重算）
必须存在的原因，它同时也是「特征库丢了」的自愈手段。换用 `cos` 后端则没有这个问题
（冷启动从 COS 拉回全量缓存只需 1~3 秒），但**换介质后桶是空的，必须手工全量重建一次**。

### 手动建库入口（应急）

两条路，按「想不想动小程序」选：

#### 路 A：小程序管理后台（最省事，一次建的少）

我的 → 管理后台 → 底部 **特征库维护** 卡片 → 点「开始」后二选一：

| 选项 | 行为 | 适用 |
|---|---|---|
| 只补缺失的（推荐） | `onlyMissing: true`，服务端跳过已有向量 | 日常补齐 |
| 全部重新计算（慢） | `force: true`，忽略已有判断全量重算 | **特征库被清空后的恢复** |

> 后端接口：`buildAiIndexAll`（admin）/ `buildAiIndex`（member，单校）。
> 单次调用给云函数 10 秒预算（`ACTION_TIMEOUT_MS` 默认 15s）。客户端 `callFunction`
> 约 3 秒就会报 `-504003`，但**云端仍会跑完**，页面会如实显示「后台处理中」而非失败。
> 猫多时一次建不完，多点几次即可 —— 增量模式幂等，已入库的不会重复计算。

#### 路 B：云开发控制台手工触发（一次建最多，推荐用于「换介质后填桶」）

小程序端按钮一轮最多 10 秒，而控制台云端测试不受客户端 3 秒限制，能把预算给到
云函数超时上限（控制台可配，默认 20s，最高 60s）。

微信开发者工具 → 云开发 → 云函数 → `catcampus` → **云端测试**，测试参数填：

```json
{ "Type": "Timer", "TriggerName": "aiIndexRebuild", "budgetMs": 45000, "photosPerCat": 3 }
```

- `aiIndexRebuild` = **force 全量重建**（忽略云库 `aiIndexAt` 记账，全部重算）
- `aiIndexDaily` = 增量补齐（只建没记过账的猫）

⚠️ **换存储介质（例如从 sqlite 切到 cos）之后必须用 `aiIndexRebuild`**：
桶是空的，但云库里每只猫的 `aiIndexAt` 还记着「已入库」，增量模式会把它们
**全部跳过**（日志里 `built=0, skipped=N`，桶依旧是空的）。只有 `force` 能打破这个死锁。

**配套操作**：把云函数的**执行超时**调到 60s（控制台 → 云函数 → 配置），
否则 `budgetMs: 45000` 会被平台提前掐断。改完点几次直到返回里 `timedOut: false`。

**看结果**：云函数日志会打一行

```
[timer] aiIndexRebuild 完成 {"processed":1,"built":12,"skipped":0,"timedOut":false}
```

`built` 是本次真正写入的猫数；`timedOut: true` 表示预算耗尽还没建完，再触发一次即可
（force 模式会重算已建的猫，属浪费但无害；想省事就改用 `aiIndexDaily` 续建）。

最后 `curl https://你的域名/health` 确认 `indexed` 等于猫档案总数、`indexBackend` 为 `cos_store`。

> 这两个 TriggerName 只挂在**定时器白名单**里（`index.js` 的 `runTimer`），
> 不在 `ACTIONS` 表内 —— 小程序端无论如何调不到，也不会被伪造的 Timer event 误触。
> 行为由 `scripts/test_timer_index_rebuild.js`（17 项）锁定。

### indexed 长期为 0 的排查顺序

1. **`AI_ENDPOINT` 是否真的配到了云函数环境变量上** —— 最常见。
   没配的话识别全程走本地占位引擎，`/v1/recognize` 一次都没发出过，特征库自然是 0。
2. **识别服务是否重启过 / 特征库是否持久化** ——
   `provider=onnx` 且确实识别过却 `indexed=0`，基本就是这项。
3. **鉴权或网络不通** —— 服务返回 503 / 连接超时，云函数日志里会有对应报错。
