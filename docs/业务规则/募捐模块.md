# 咪咪筹（MimiChou）—— 校园猫咪医疗 / 绝育筹款

> 面向：全校学生（发起 + 捐助）、社团管理员（审核 + 核销）、超管（审计）。
> 状态：v2 已实现（云端 + 小程序端），2026-11-07 从「管理员发起的医疗求助」升级为水滴筹式众筹。
> 收款方式：**微信虚拟支付** `lib/vpay.js`。**不接入支付宝 / 第三方收款码**，原因见第二节。

---

## 一、产品定位

| | 旧版（医疗求助） | 咪咪筹（现在） |
|---|---|---|
| 谁能发起 | 仅管理员 | 任何登录用户（普通用户需审核） |
| 筹款类型 | 医疗 | 医疗 + 绝育 |
| 绑定对象 | 单只猫 | 单只猫（**必须已建档**，不接受凭空发起） |
| 材料 | 无 | 诊断证明 / 费用清单 / 患处照片 / 其他，最多 9 份 |
| 状态 | active / closed | 待审 → 进行中 → 已完成 / 已结束 |
| 资金去向 | funds 的 income 记录 | 同左，另带 campaignId 维度 |

一句话：**先有猫档案，再有筹款；钱进公开账本，花出去要有票据。**

## 二、支付方案（重要，含「能不能放支付宝扫码」的结论）

### 2.1 结论：不能在小程序里放支付宝扫码

三条硬约束，任何一条都足以否掉这个方案：

1. **微信小程序运营规范禁止引导站外支付**。在小程序内展示支付宝收款码、跳转支付宝、诱导「加微信转账」都属于违规，审核直接驳回；上线后被举报会被限制支付能力甚至下架。这不是「大概有风险」，是明文规则。
2. **个人主体开不了微信支付商户号**，也开不了支付宝当面付的商户能力。所谓「支付宝扫码」只能落到**个人收款码**——而个人收款码没有异步回调，服务端无法收到「谁付了多少」的通知，只能靠人工对账：重复入账、漏记、伪造截图全都无法识别。
3. **资金进入个人账户 = 非法集资高风险**。以公益名义公开募资、款项进个人支付宝，一旦被认定「向社会公众吸收资金」，性质就不是平台违规而是法律问题。真要做合规公益募捐，钱必须进**具有公开募捐资格的慈善组织账户**或**对公账户**。

所以本模块的支付只有一条路：**微信虚拟支付**（个人主体下唯一可用的收款通道）。

### 2.2 现状方案（已在用）

- 一笔捐助 = 购买一个虚拟「爱心赞助」道具（`VPAY_DONATE_PRODUCT_ID`，默认 `donate_1`）。
- 支付成功 → 微信推送发货事件 → `vpay.onGoodsDeliver` → `donation.applyDelivery` 钩子：
  - 按 `outTradeNo` 幂等去重
  - 写 `funds`(income / category=donation) + 原子累加 `campaign.raisedAmount` 与 `donorCount`
- ⚠️ **合规灰区**：虚拟支付本意是卖虚拟商品，用它收真实治病善款属于平台规则边缘用法。个人主体只能先这样。

### 2.3 三条升级路线（按合规程度排序）

| 路线 | 做法 | 成本 | 适用 |
|---|---|---|---|
| A. 企业 / 个体户主体 + 微信支付商户号 | 换成标准 JSAPI 支付，资金进对公账户，提现走公对公 | 需营业执照、对公账户、类目资质 | 想长期做、金额较大 |
| B. 挂靠有公募资格的基金会 | 接入慈善组织（如腾讯公益）的筹款页，本小程序只做导流与档案展示 | 需合作洽谈 | 最合规，但自主性低 |
| C. 不做在线收款 | 只发布求助信息，捐助走线下，管理员录入「线下捐助」记录 | 零成本、零风险 | 校内小额、熟人场景 |

> 代码层面已为 A 预留：`donateToCampaign` 只依赖 `vpay.createOrder` 的返回结构，
> 换成真实支付时替换该函数即可，前端不用动。

## 三、角色与流程

```
普通用户发起                    管理员发起
   │                              │
   ├─ createCampaign ─→ pending   └─ createCampaign ─→ approved
   │                        │
   │                 管理员审核 reviewCampaign
   │                   ├─ 通过 → approved（公开可见，可捐助）
   │                   └─ 驳回 → rejected（仅发起人/管理员可见，附原因）
   │
   └─→ 公开展示 ─→ 捐助（vpay）─→ funds 入账 ─→ 管理员记支出（票据）
                                              └─ 支出 ≥ 已筹 → 自动 fulfilled
```

- 审核通过后才进入公开列表；未通过的详情只有发起人和管理员能打开。
- 同一只猫**同时只能有一条进行中**（approved + active），防止重复筹款。
- 同一账号**同时最多 2 条待审**，防刷。
- 发起人可随时结束；管理员也能结束（用于造假/纠纷处理）。

## 四、数据模型

### 集合 `medical_campaigns`（沿用旧集合名，字段已扩展）

| 字段 | 说明 |
|---|---|
| `catId` / `catName` / `catAvatar` | 绑定的猫 + 快照（列表免联表） |
| `kind` | `medical`（医疗）/ `tnr`（绝育） |
| `title` / `reason` | 标题（4~40 字）/ 情况说明（10~1000 字），过内容安全 |
| `goalAmount` / `raisedAmount` | 目标 / 已筹（元，上限 20 万，下限 100） |
| `expenseTotal` | 已支出（元），由票据累加 |
| `donorCount` | 捐助人次（支付成功后 `_.inc(1)`） |
| `materials[]` | `{ type, fileID, note, public, at }`，type ∈ diagnosis/invoice/photo/other |
| `status` | `active` / `fulfilled` / `closed` |
| `reviewStatus` | `pending` / `approved` / `rejected`；驳回时带 `reviewNote` |
| `applicantOpenid` / `applicantName` / `applicantIsAdmin` | 发起人 |
| `contact` | 联系方式，**仅管理员可见**（审核回访用） |
| `endDate` | 截止日期，可空；填了必须 ≤ 90 天 |
| `updates[]` | 进展 `{ text, images, createdAt }`，发起人或管理员可发 |
| `schoolId` / `createdBy` | 学校隔离 + 创建者 |

### 集合 `funds`（复用「收支公示」）

- 捐助 = `type:'income', category:'donation'`，带 `campaignId` / `catId` / `donorName`（已脱敏）/
  `outTradeNo`（对账）/ `donorOpenid`（内部，不展示）。
- 支出 = `type:'expense', category:'medical'`，带 `campaignId` 与 `proof`（票据图）。
- 筹款本身**不持有资金**，只是 funds 上的一个维度 → 首页/资金公示的收支汇总天然包含它。

## 五、云函数 Action

| action | 角色 | 说明 |
|---|---|---|
| `createCampaign` | user | 发起；普通用户 → pending，管理员 → approved |
| `listCampaigns` | public | `scope=public`（默认，已通过）/ `mine` / `review`（管理员） |
| `getCampaign` | public | 详情；未通过仅发起人/管理员可见；材料按 `public` 过滤 |
| `donateToCampaign` | user | 创建虚拟支付订单（前置校验审核状态/同校/不能自捐） |
| `reviewCampaign` | admin | 通过 / 驳回（驳回必须写原因） |
| `closeCampaign` | user | 发起人或管理员结束 |
| `reportCampaign` | user | 举报 → 通知超管，不在前台暴露处理过程 |
| `addCampaignUpdate` | user | 发起人或管理员发进展 |
| `addCampaignExpense` | admin | 记支出（仅管理员，避免自证）；花完自动结项 |
| `listCampaignDonations` | user | 完整名单（仅发起人/管理员） |
| `listMyDonations` | user | 我的捐助记录 |

钩子：`index.js` 启动时 `vpay.setDeliverHook(donation.applyDelivery)`。

## 七、权限与隐私

| 数据 | 谁能看 |
|---|---|
| 未通过审核的筹款 | 发起人、管理员 |
| 材料原图 | 发起人、管理员；其他人只看 `public:true` 的 |
| 隐藏材料 | 只显示「另有 N 份仅管理员可见」 |
| 联系方式 | 仅管理员 |
| 捐助人 | 只显示脱敏昵称（张*），不存手机号 |
| 完整捐助名单 | 发起人、管理员 |

- 端上不出现「AI」措辞、不展示审核权重与风控规则；驳回文案只给「材料不完整」这类中性表述。
- `getCampaign` 的字段过滤全部在服务端完成，前端不承担权限判断（前端判断可绕过）。

## 八、风控规则一览

| 规则 | 值 | 目的 |
|---|---|---|
| 目标金额 | 100 ~ 200000 元 | 防天价与滥用 |
| 单笔捐助 | ≤ 200000 元 | 同上 |
| 标题长度 | 4 ~ 40 字 | 防空白/刷屏 |
| 说明长度 | 10 ~ 1000 字 | 保证有信息量 |
| 截止日期 | ≤ 90 天 | 避免长期挂单 |
| 同猫进行中 | 唯一 | 防重复筹款 |
| 待审上限 | 2 条/人 | 防刷 |
| 材料数量 | ≤ 9 | 控制包体 |
| 内容安全 | 标题 + 说明 + 进展 + 支出说明 | 合规 |

## 九、部署前置（否则捐助会失败）

1. **MP 后台开通「虚拟支付」**，在【虚拟支付 → 道具管理】创建道具，ID 与
   `lib/donation.js` 的 `DONATE_PRODUCT_ID`（默认 `donate_1`，可用 `VPAY_DONATE_PRODUCT_ID` 覆盖）一致。
2. **配置 vpay 环境变量**：`VPAY_OFFER_ID / VPAY_APP_ID / VPAY_APP_SECRET / VPAY_APP_KEY / VPAY_SANDBOX`
   `VPAY_MSG_TOKEN / VPAY_ENCODING_AES_KEY`（推送验签）。详见 `lib/vpay.js` 头部注释。
3. **消息推送**：把虚拟支付的发货/退款推送指向云函数 `vpayNotify`。
4. **部署后调一次 `initCollections`**（`medical_campaigns` 已在 `COL` 注册）。

> 未配置虚拟支付时，发起/审核/进展/材料/列表都可用，只有「捐助」会报错——便于先上线信息流。

## 十、v2 已知取舍

- 审核只在「通过/驳回」两态，没有打回修改后再提交的独立流程（驳回后改内容需重新发起）。
- 更新时间与热度排序简化为「创建时间倒序」，未做推荐/置顶。
- 未做提现/结算：钱由微信虚拟支付结算到主体账户，平台不托管，也没有「筹款余额」概念。
- 材料只支持图片，暂不支持 PDF 诊断书（可后续接 `wx.chooseMessageFile`）。
- 举报只通知超管，没有前端处理结果回执。
