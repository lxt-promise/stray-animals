# 账号与用户管理（登录凭据 · 权限配置）

> 2026-10-30 定稿。个人主体小程序拿不到微信官方 `getPhoneNumber`（需企业主体 + 已认证），
> 所以「多设备登录同一份档案」这条路由自建账号体系承担；超管的用户管理则是这套体系的后台配套。

## 一、账号规则（收紧为手机号 / 邮箱）

| 项 | 规则 |
|---|---|
| 账号格式 | **只允许 11 位手机号或邮箱**（正则见 `assertAccountFormat` / 前端 `util.isValidAccount`） |
| 密码 | ≥ 6 位，`scrypt(密码, 随机盐)` → 存 `salt:hash`，**绝不落明文**；接口返回前 `sanitizeUser` 摘掉 `password` |
| 唯一性 | `account` 全局唯一，重复注册 / 换绑都返回 409 |
| 手机号同步 | 账号填手机号时自动写 `phone`（手机号账号本身就是联系方式）；填邮箱时**不清空**已有 `phone`（静默删数据更糟） |
| 改账号 | 必须验**当前密码**（`oldPassword`）+ 查重：谁能改账号谁就能接管这份档案 |
| 改密码 | 需原密码（`updateProfile.password` 走同一套校验） |
| 多设备 | `linkedOpenids`：设置账号时把当前 openid 并入；账号密码登录时把新设备 openid 并入 → 换设备自动登录仍是同一份档案 |

**为什么不再允许自由用户名**（2026-10-30 收紧）：用户名不可验证、不可找回（换设备时根本想不起当初填的什么），
还容易和别人撞车（昵称本来就允许重名）。手机号 / 邮箱是唯一且可验证的标识，账号体系才有意义。

登录失败一律报「账号或密码错误」——不透露格式规则，等于不给撞库者缩小范围。

## 二、「账号与安全」页交互

- **未设置账号**：直接摊开「设置账号密码」表单（这一步没有别的入口）；
- **已设置账号**：表单**默认收起**，只显示当前账号（脱敏）+ 三个入口 ——
  `修改账号` / `修改密码` / `登录其他账号`，点开才展开；再点同一个入口即收起，另有「收起」按钮。
  理由是：一进页就摊着三行输入框，看起来像「还没设置成功」，用户会以为刚才那步没生效。
- **没有手机号卡片**：账号行已经把手机号显示出来了（脱敏），页面下方再放一张「当前手机号 + 保存手机号」
  的卡片是同一个号码出现两次，纯噪音 —— 已删除；`phone` 仍由账号（手机号）自动同步。
- 账号已存在 → 自动切到「登录已有账号」模式，引导用密码登录（多设备复用同一账号）。

## 三、用户管理（超级管理员 · 全站）

后台（`/pages/admin/admin`，**手风琴分板块**）新增「用户管理（全站）」面板：搜索 + 角色筛选 + 列表 + 一键配角色。该面板默认收起，与其他板块（打卡可见性 / 校园管理 / 重复档案 / 学校申请 / 成员管理 / 上传记录 / 识别引擎 / 特征库 / 确认样本）并列，点头部展开。

| 接口 | 权限 | 说明 |
|---|---|---|
| `listUsersAdmin` | `requireSuper` | 跨校区列用户；支持 `keyword`（昵称 / 账号 / 手机号前缀，`db.RegExp` + `escapeReg`）、`role`、`schoolId`、`size`；返回脱敏字段与 `roleCount` |
| `setUserRole` | `requireSuper` | **只改 `role`，绝不动 `schoolId`** |

与既有「成员管理」的区别（**不要合并**）：

| | 成员管理 `listMembers` / `setRole` | 用户管理 `listUsersAdmin` / `setUserRole` |
|---|---|---|
| 范围 | 本校区 | 全站（跨校区） |
| 谁能用 | 社团管理员 | 仅超管 |
| 改角色时 | 顺带写 `schoolId: me.schoolId`（把人拉进本社团，**这是它的意图**） | **绝不动** `schoolId` |
| 越权风险 | 低（只动本校） | 高：A 校管理员若能把 B 校的人提成管理员，学校隔离就失效了 —— 所以收在超管手里 |

脱敏与边界：
- 列表**不下发** `openid` / `password`；账号与手机号只给中段打码后的样子（`138****8000`、`zh****@school.edu.cn`）。
- `role:'user'`（历史口径）归一为 `visitor`，筛选「访客」时两种写法都能命中。
- 不能降级自己、不能改超管身份（由 `SUPER_ADMIN_OPENIDS` 决定）、非法角色 400。
- 排序 `orderBy('createdAt')` 失败（缺复合索引）时自动退化成内存排序 —— 后台页面不该因为索引缺失打不开。

## 四、部署与运维

- 两个新 action（`listUsersAdmin` / `setUserRole`）随云函数一起上传即可，不需要新建集合。
- 忘记密码没有找回通道（个人主体下无短信能力）：只能由**超管在后台把该用户降级/处理**，
  或用户用原微信 openid 登录后重设（`registerAccount` 对已设账号返回 409，
  此时要先在数据库里清掉 `account` / `password` 字段）。
- 排查「改账号失败」：先看服务端日志 `updateProfile 当前密码不正确`（没传 `oldPassword`）
  还是 `该账号已被使用`（撞车）。

## 六、测试账号切换（超管自测其他角色）

**背景**：超管只有一个微信身份，看不到「普通用户 / 社团成员」眼里的界面 —— 位置脱敏、工作台入口、
建档按钮、积分卡全都不一样。让别人帮忙点一遍既不现实，也没法反复复现。

**位置**：「我的 → 账号与安全」页顶部「测试账号切换」卡片（**只有超管能看到**）。
三个槽位：管理员 / 社团成员 / 普通用户，每个槽位从**全站用户列表**里选一个账号绑定，再点「切换」。

**机制是服务端代理解析身份（view-as），不是改库里的 role**：

1. 客户端把 `actAs=<用户 _id>` 随每次云调用带上（存本机缓存，退出即清）；
2. 服务端先按**真实 openid** 找到调用者（`getMe`），只认 `SUPER_ADMIN_OPENIDS` 白名单；
3. `actAs` 必须命中该超管自己配置的三个槽位之一，且目标不是超管、不是自己、且有 openid；
4. 之后所有 handler 拿到的 `me` 就是那个账号 —— `requireRole`、`sanitizeCat`（位置脱敏）、
   积分记账全部按被切换账号生效。

| 接口 | 权限 | 说明 |
|---|---|---|
| `testAccounts` | `requireSuper` | 读三个槽位 + 绑定账号的昵称 / 角色 / 脱敏账号 |
| `setTestAccounts` | `requireSuper` | `{slot:'admin'|'member'|'normal', userId}`；`userId=''` 解绑 |

配置落地：写在**超管自己的 user 文档** `testAccounts: { admin, member, normal }` 字段里，**不新建集合**。

**硬边界**（都有测试覆盖）：

- 普通用户 / 非白名单管理员调这两个接口一律 403；伪造 `actAs` 也 403（不按别人解析）；
- 不能切自己（400）、不能切另一个超管（403）、未绑定的账号 403、缺 openid 的脏数据 400；
- 测试身份下禁止 `registerAccount` / `loginWithPassword`，以及 `updateProfile` 里的密码 / 账号字段（403）
  —— 否则一次测试会把某个账号的登录凭据并到别人身上；
- 测试身份下 `login` / `homeInit` 走**只读**分支：不合并重复档案、不发新手礼包 / 超管礼遇，
  真实超管档案不会被「切换」这一下改动；
- 客户端 `isSuper()` 在 `actAs` 非空时直接返回 `false`，后台入口 / 建档按钮会按测试账号隐藏；
- 前端启动时若 `homeInit` 返回 403/404（超管解绑、测试账号被删），自动清缓存回到真实身份。

**注意**：在测试身份下产生的打卡 / 积分 / 档案修改，都会**记在被切换账号身上**（这才叫真实测试）。
「我的」页顶部和账号页都有紫色横幅 + 「退出」，避免忘了自己在测试态、把对方数据当成自己的丢了。

`node scripts/test_test_actas.js`（33 项）覆盖上面的权限、非法目标、身份解析与凭据保护。
