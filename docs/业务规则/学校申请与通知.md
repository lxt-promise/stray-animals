# 学校申请与通知（入校 / 建校审核）

> 2026-10-30 修订。起因：用户反馈「申请绑定学校后管理员未收到任何通知，且可以点多次绑定」；
> 同日追加：推广期**暂时注掉绑校审核**（选校立即生效，后期可一键恢复）、**同一学校不同校区要按不同 ID 区分且不能建重**，
> 以及**建校收口为管理员专属**（绑定人人可选、选中即生效；新建学校只有管理员能建，且管理员建校免审）。

## 一、问题与结论

| 问题 | 根因 | 修复 |
|---|---|---|
| 管理员收不到申请通知 | 项目**此前没有任何通知通道**，审核入口只在超管后台，要管理员主动进去翻 | 新增 `notices` 站内通知 + 工作台待办/红点；订阅消息作为可选增强 |
| 可以重复提交申请 | 后端虽有「同用户只保留一条 pending」的兜底，但**前端入口没锁**，用户能一直点 | 待审期间选校 / 新建入口置灰 + 按钮防连点 + 后端返回明确 `reason` |
| 管理员选校也要提申请等审核 | 2026-10-26 关闭「选中即绑定」后门时，**没有给管理员留豁免** | 新增 `bindSchoolSelf`（`role:'admin'` 服务端校验），管理员选校直接生效 |
| 提交申请后无法撤销 | 待审期间入口全灰，却**没有撤回通道**；管理员不审就彻底卡死 | 新增 `withdrawSchoolApply`，待审横幅上提供「撤回」，撤回后入口解锁 |
| 推广期审核太挡人 | 新用户选完学校要等超管审核，人不在 / 延迟 → 直接流失 | 服务端开关 `SCHOOL_REVIEW`（默认 `off` = 免审），选校**立即生效** |
| 谁都能建校，下拉被垃圾校区刷满 | 免审是「放开绑定」，建校跟着一起放开就成了**人人可开数据域**：学校列表被「测试」「asdf」占满，用户反而选不到自己的学校 | 建校**收口为管理员专属**（`canCreateSchool`）：普通用户传 `name` 一律 403 并提示「从列表里选 / 联系管理员」；管理员建校立即生效且**不看审核开关** |
| 同一学校不同校区会建重 | 学校**完全没有查重**：`createSchool` / 审核建校都是直接 `add`，同名同校区能建出 N 份 | 去重键 `schoolKey = 校名 | 校区`，建校前查重（撞上就复用），超管还能查存量重复 |

## 二、申请流程（现行，取决于 `SCHOOL_REVIEW` 开关）

```
用户选校 / 填新建资料
   │
   ├─ 传 name（新建学校）—— 仅管理员，且不看 SCHOOL_REVIEW
   │     ├─ 管理员（admin / super）→ createSchoolDirect：查重 → 建校（或复用已有的）→ 立即绑定
   │     └─ 普通用户 → 403「仅管理员可创建学校，请从列表中选择你的学校」
   │
   └─ 传 schoolId（绑定已有学校）—— 人人可绑
         ├─【免审 off（推广期默认）/ bind】→ bindUserToSchool：立即绑定，返回 { status:'bound' }
         └─【审核 on / create】
               ├─ 管理员 → bindSchoolSelf：直接绑定，免审（并撤掉本人待审，
               │            否则超管审完又把他绑回旧目标）
               └─ 普通用户 → 填理由 → applySchool
                     ├─ 已有 pending → { status:'pending', reason:'already_pending' }（前端锁入口）
                     └─ 无 pending   → 落 school_applies(pending) → 通知超管 → { status:'submitted' }

待审期间：普通用户入口锁死；可点横幅上的「撤回」解锁后重选
超管：后台审核（通过=绑定，驳回=退回）
审核通过后：用户端下次进「我的」页自动同步为新学校（不必重启小程序）
```

- **待审期间保持原绑定**（不会因为提交申请就换校），审核通过才切换。
- 审核动作 `handleSchoolApply` 为 `requireSuper`（**只有超管能审**），因此通知也只发给超管；给普通管理员摆一个他点不动的待办数字只会造成困惑。
- 建校权限下发给前端（`mySchoolApply.policy.canCreate`）：普通用户看到的是「没有我的学校？**联系管理员添加**」，点下去也进不去表单（不是填完才 403）。
- 管理员建校**不看 `SCHOOL_REVIEW`**：他是各校数据的维护者，让他给自己提一条建校申请、再等超管审一遍没有意义（与 `bindSchoolSelf` 同理由）。所以 `school_applies` 里只会剩下 `type:'join'`。
- 免审模式下**理由不再是必填**（服务端不强校验，前端也隐藏该输入框），但校名 / 校区 / 简介**仍过文本安全检测** —— 建校内容会展示给全校。

## 二·补、推广期免审开关（`SCHOOL_REVIEW`）

配云函数环境变量，**不配 = `off`（免审）**：

| 取值 | 含义 |
|---|---|
| `off` | 绑定立即生效（**推广期默认**）；建校恒为管理员专属且免审（不受本开关影响） |
| `on` | 绑定走管理员审核（推广期结束后改这个，**不用改代码**）；建校同上，仍只归管理员 |
| `bind` | 只放开「绑定已有学校」，建校仍只有管理员能建 |
| `create` | 仅保留取值兼容：建校已不经过审核，配它等价于「绑定仍需审核」 |

- **判定只在服务端**：读 `process.env.SCHOOL_REVIEW`，前端传什么都不影响。前端经 `mySchoolApply.policy`（`reviewBind` / `reviewCreate` / `mode`）拿到结果，**只用来决定界面**（弹不弹理由框、文案怎么写）。
- **显式判空而不是 `|| 'off'` 兜底**：空字符串也算「配了」，用 `||` 会把配错的值悄悄吞成默认值（项目里「改了不生效」的头号元凶）。
- 前端默认值取「需要审核」：`policy` 拉取失败时退化成审核模式（多填一个理由）也好过退化成免审（服务端要求理由 → 用户直接卡死）。
- 前端拿到 `status !== 'bound'` 时**不会**当作切换成功（服务端可能已被改回审核模式），走「已提交，等待审核」分支。
- ⚠️ 免审 ≠ 放弃边界：隐藏校（测试校园）照样进不去（`assertSchoolBindable`），权限照样由 `requireRole` 校验。
- ⚠️ 合规提醒：当初关闭「选中即绑定」是因为「知道 schoolId 就能挤进任意学校数据」。免审是**推广期的主动取舍**，拉新结束后建议把开关改回 `on`。

## 二·补二、建校权限（与免审开关无关，2026-10-30 定稿）

一句话：**绑定人人可选、选中即生效；新建学校只有管理员能建，且管理员建校免审。**

| 动作 | 谁能做 | 是否审核 |
|---|---|---|
| 绑定已有学校（传 `schoolId`） | **所有人** | 由 `SCHOOL_REVIEW` 决定（推广期免审） |
| 新建学校（传 `name`） | **仅超管 / 社团管理员**（`canCreateSchool`） | 免审，建完立即绑定 |

为什么建校不能跟着免审一起放开：

1. 学校是**数据隔离的支点**（猫档案 / 打卡 / 统计全按 `schoolId` 切），每建一所就开一个新的数据域；
2. 人人能建 → 下拉被「测试」「asdf」「xx大学」刷满，用户反而**选不到**自己的学校，只能自己再建一份，于是同一所学校被切成十几摊；
3. 建校内容会展示给全校（校名 / 简介），本来就该有人把关；文本安全检测因此照跑。

实现要点（都在服务端，前端只是照 `policy.canCreate` 渲染）：

- `canCreateSchool(me) = isSuper(me) || isAdmin(me)`；
- `applySchool` **第一行**就判 `!isJoin && !canCreateSchool(me) → 403`，
  顺序必须在 `SCHOOL_REVIEW` 判断**之前**（否则 `off` 时普通用户照样建校）；
- `createSchoolDirect` 再挡一次：它是「建校」这件事的唯一出口，
  将来若被别的 action 直接调用，权限判定不该依赖调用方记得先判；
- `mySchoolApply.policy` 增发 `canCreate`，前端据此把入口文案换成
  「没有我的学校？**联系管理员添加**」，并在点开 / 提交时直接挡住（不是填完才报错）。

## 三、通知：两条通道

### 1. 站内通知（必定可用，零外部依赖）

- 新集合 **`notices`**（已在 `lib/core.js` 的 `COL` 注册，`initCollections` 自动建表）。
- 申请提交后，`lib/notify.js` 的 `schoolApplySubmitted` 给 `SUPER_ADMIN_OPENIDS` 里每个超管**批量写一条**（一次 `add` 数组，不是循环 await）。
- 字段：`type` / `refType` / `refId` / `title` / `content` / `read` / `createdAt`。
- 前端：
  - 「我的」页「**工作台**」菜单项旁**未读红点**（菜单项本身管理员+超级管理员都可见，但红点只有超管会 >0）；
  - 工作台是**独立页 `/pages/workbench/workbench`**（管理员+超级管理员都能进），页内「待审入校 / 建校申请 N」区，>0 时高亮，点击直达后台；
  - 打开超管后台即把 `school_apply` 类通知标记已读（否则红点永不消失）。
  - ⚠️ **分层约定**：工作台（基础社团管理工具）= 管理员 + 超级管理员可见；「**超级管理员后台**」（`/pages/admin/admin`，手风琴分板块：打卡可见性 / 校园管理 / 重复档案 / 学校申请 / 用户管理全站 / 成员管理 / 上传记录 / 识别引擎 / 特征库 / 确认样本）= **仅超级管理员**可见，入口同样在「我的」页菜单（带 `wx:if="{{isSuper}}"`）。

### 2. 微信订阅消息（可选增强，需配置）

- 云函数环境变量 `SUBSCRIBE_TMPL_SCHOOL_APPLY` 配模板 ID 后自动启用，**不配则静默跳过**（绝不让提交失败）。
- 授权：超管在「我的 → 工作台 → 开启申请通知」点一次 `wx.requestSubscribeMessage`（一次性订阅，可反复点补额度）。
- 模板 ID 只存在云端，前端通过 `notifyConfig` action 获取。
- ⚠️ **模板字段约定**（MP 后台选模板时必须带这三个关键词，否则微信拒发）：
  `thing1` 标题 / `thing2` 内容 / `time3` 时间。
- 未授权（43101）是预期内的，只记 warn 不刷错误日志。

## 四、防重规则

- **后端**：`applySchool` 开头查同用户 `status:'pending'`，命中直接返回 `reason:'already_pending'`（不新增记录）。
- **前端**：
  - `applyLocked`（有待审**且非管理员**时为真）→ picker `disabled`、新建入口文案改为「已有待审申请，等待管理员处理」并置灰；
  - `openSchoolPicker` / `toggleSchoolForm` 入口处二次拦截（防绕过 UI）；
  - `submitting` 标志 + 按钮 `disabled`，请求未回时再点不发第二个请求；
  - `load()` 末尾统一兜一次 `schoolPickSide='待审'`（`loadSchoolApply` 与 `loadSchools` 并行，谁后返回不确定）。
- 超管走 `createSchool` 直接建校，不受待审锁限制。
- ⚠️ **锁只有一处判定源**：`loadSchoolApply` 里按「有待审 + 非管理员」算，其它地方不再各自 `setData({applyLocked:true})` —— 两处各判一次迟早不一致（管理员免审后正是踩这点）。

## 四·补、学校怎么存：校区 = 独立档案 + 去重键

**存储模型**（集合 `schools`，一条 = 一个校区）：

```
schools
 ├─ _id: 'sch_jiulonghu'   name:'东南大学'  campus:'九龙湖校区'  schoolKey:'东南大学|九龙湖'
 ├─ _id: 'sch_sipailou'    name:'东南大学'  campus:'四牌楼校区'  schoolKey:'东南大学|四牌楼'
 └─ _id: 'sch_dup'         name:'东南大学'  campus:'九龙湖校区'  ← 脏数据（建重了）

users.schoolId   → 指向某一个校区 _id（一个用户同一时刻只属于一个校区）
cats.schoolId / sightings.schoolId → 同样指向校区 _id，所以两个校区的猫档案、打卡、统计天然隔离
```

- **不同校区就是两所独立档案**：各自的 `_id`、各自的猫档案 / 打卡 / 地图范围 / 资金账。`listSchools` 的展示名是 `name · campus`，选校下拉里能明确区分。
- 为什么要分开而不是「一所学校 + 校区字段」：两个校区通常隔着几十公里，猫群和志愿者根本不是同一批；合成一条的话地图只能画一个 bounds、统计也混在一起，没法用。

**去重键 `schoolKey = 校名 | 校区`**（`schoolKeyOf()`）：

- 归一化：去空格 / 大小写 / 常见标点，并吃掉末尾的「校区 / 校园 / campus」后缀 —— 所以「九龙湖校区」和「九龙湖」是同一所。
- **校区计入 key**：只按校名判重的话，第二个校区会被误判成重复而建不出来。
- 撞上同名同校区 → **不建副本**：免审建校直接绑到已有的（`reused:true`，前端提示「已存在，已为你切换过去」）；超管后台建校 / 改名撞车则 **409** 并给出已存在的校名。

**存量治理**（`schoolKey` 是 2026-10-30 才加的字段，历史学校没有它）：

- 查重对老数据依然有效：快路径 `where({ schoolKey })` 查不到时，回退到「全量拉取 + 逐条按 key 比对」（学校是几十所的量级，比维护索引划算）。
- 超管后台「校园管理」里两个按钮：
  - **检查重复校区** → `findDuplicateSchools`，列出所有同名同校区组（含每组 `_id` 与建校人）。**只报告不自动合并** —— 合并要把猫档案 / 打卡 / 任务全部改挂 `_id`，判错没法回滚，必须人工看着数据决定。
  - **修复去重键** → `backfillSchoolKeys`，给历史学校补上 `schoolKey`（并行 `Promise.all`，不是串行 await 循环），补完查重就回到一次 where 命中。
- 改名 / 改校区会同步重算 `schoolKey`（不同步的话，查重会拿旧 key 比新名字，表现为「改完名后同名学校查不出来」）。

## 五、管理员免审绑校（bindSchoolSelf）

- **权限收在服务端**：action 注册 `role:'admin'`，由 `requireRole` 校验。普通用户直接调会得到 **403**，前端传什么都不算数。
- **普通管理员（admin）仍过 `assertSchoolBindable`**：隐藏校（测试校园）只对超管开放，admin 不能靠直绑绕进去；`isSuper` 命中白名单时才放行隐藏校。
- **直绑后撤掉本人待审**：条件更新 `status:'pending' → 'withdrawn'`。否则他已经换好学校，超管待审列表里还挂着「申请加入 A 校」，审完又把他绑回去。
- 前端：管理员选中学校 → 弹一次确认 → `bindSchoolSelf` → `refreshUser` + `setSchool` + 整页 `load()`（换校会切换图鉴 / 打卡 / 地图的数据口径，不重拉表现为「换了学校但什么都没变」）。
- 管理员的待审横幅仍在（如实告知），但下方多一行「你是管理员：也可直接在上方切换学校，无需等待审核」。

## 六、撤回待审申请（withdrawSchoolApply）

- 起因：待审期间入口全灰，若管理员长期不审，用户既不能换校也不能重建 —— 是个死局。
- 条件更新 `{_id, openid, status:'pending'} → 'withdrawn'`，三条同时命中才算数：
  - 撤不了**别人的**（带 `openid`）；
  - 撤不了**已通过 / 已驳回**的（只匹配 `pending`）；
  - 重复撤回返回 **409 该申请已处理**。
- 撤回后立即解锁入口，用户可重新选校或新建。
- 撤回的记录不出现在超管待审列表（`listSchoolApplies` 查 `pending`），也不会污染「我的申请」状态。

## 七、审核通过后自动生效

`handleSchoolApply` 只改云端 `user.schoolId`，客户端 `globalData` 仍是旧校 —— 用户会看到「申请已通过」但整页数据还是老学校。

修复在 `loadSchoolApply`：发现「无待审 + 有 approved + `approved.schoolId` ≠ 当前学校」时，补一次 `refreshUser` + `getSchool` + `setSchool` + `load()`。
去重用 `_syncedSchoolId`（记录上次同步过的学校 id）而不是布尔位 —— 布尔位会让用户第二次申请换校时同步失效。

6. 重新**编译上传小程序**（改了 `mine` / `admin`）。

## 十、设计取舍备忘

- 通知用 **await 而不是 fire-and-forget**：通知是本次提交的关键产物，fire-and-forget 在实例回收时会丢，申请就一直挂着没人审（正是本次要修的问题）。但异常必须吞掉 —— 通知失败不能让用户看到「提交失败」，他的申请其实已落库。
- 收件人取 `SUPER_ADMIN_OPENIDS`（openid 白名单）而非查 role：审核权限就是 `requireSuper`，按 role 查会误发给审不了的人。
- 管理员免审的**边界不是 role 本身而是 data**：关掉「选中即绑定」是因为任何人拿到 schoolId 就能挤进任意学校，而管理员本就是数据维护者。所以豁免只给 `role:'admin'`，且 admin 仍受隐藏校可见性约束 —— 放宽的是流程，不是准入。
- 撤回用**条件更新**（只匹配 `pending`）而不是「先查后写」：管理员点通过和用户点撤回并发时，只会有一个 `updated=1`，另一个拿到 409，不会把已通过的申请改回待审。
- 免审开关做成**环境变量**而不是代码常量：推广期结束的当天要能一键恢复审核，不该再排一次发布改代码。前端同步读 `policy` 自适应，所以只改服务端一处就够。
- 去重键**带校区**：不加 campus 的话「第二个校区建不出来」，比建重更致命（用户直接卡住）。归一化吃掉「校区」后缀则是为了拦住「九龙湖 / 九龙湖校区」这种无害差异。
- 查重**只拦新增、不动存量**：自动合并校区要改挂 `_id`，判错不可回滚，所以只提供只读的重复报告，由人工决定。
- 建校的三条路径（免审直建 / 超管后台 / 审核通过）都必须走同一个查重入口 `findSameSchool`；分开写迟早有一份漏掉，漏的那份就是脏数据来源。
