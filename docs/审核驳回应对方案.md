# 审核驳回应对方案：社交-笔记类目

> 驳回原文：*"你的小程序涉及用户自行生成内容（文字、图片、音/视频）的记录、分享，属社交-笔记范畴，为个人主体小程序未开放类目。"*  
> 依据：《微信小程序平台运营规范常见拒绝情形 2.1》  
> 日期：2026-10-16

---

## 一、先看清审核员到底看到了什么

审核员的判断逻辑是**功能形态匹配类目**，不是看你自称什么。他的推理链：

```
小程序里有「用户自己写文字 + 传图片」的入口
  → 这些内容会保存下来
  → 其他人能看到（公开可访问）
  → 还能分享出去
  → 这就是「社交 - 笔记」的定义
  → 个人主体未开放该类别 → 驳回
```

这个链条在喵园里**确实成立**，不是误判。命中的具体功能：

| # | 功能位置                                  | 用户生成内容                    | 是否公开                                   | 权重        |
| - | ------------------------------------- | ------------------------- | -------------------------------------- | --------- |
| ① | `sighting-post` 打卡页「**描述**」`textarea` | **自由文字**（"它在做什么？精神状态如何？"） | `listSightings` 是 `role:'public'`，全校可见 | 🔴 最高     |
| ② | `sighting-post` 照片上传                  | 用户相册图片                    | 同上，公开可见                                | 🔴 高      |
| ③ | `cat-edit` 建档页                        | 猫名 + 备注 + 照片              | 公开猫谱                                   | 🟠 中      |
| ④ | `task` 任务页 `note`、`tnr-edit` 备注       | 自由文字                      | 成员可见                                   | 🟡 低      |
| ⑤ | `member` 入社申请 `reason/experience`     | 自由文字                      | 仅管理员可见                                 | 🟢 可忽略    |
| ⑥ | 11 个页面的**分享**能力（上一轮刚补的）               | —                         | 对外传播                                   | 🔴 高（催化剂） |

**关键判断**：①+② 是「笔记」的教科书形态（**自由文字 + 图片 + 公开 + 可分享**）。  
只要这一条在，审核员就站得住脚。⑥ 是我们自己上一轮刚放大的风险面 —— 分享让"传播"从隐性变显性。

---

## 二、三条路，必须选一条

### 路线 A：改功能形态，降级为「工具-信息查询」（**推荐**）

**核心思路**：把「用户写笔记」改造成「用户填结构化的猫况记录」。同样是记录，但**形态从"创作"变成"登记"**。

理论依据：微信对「工具-信息查询」的界定是**查询 + 结构化记录**；对「社交-笔记」的界定是  
**用户创作长文/图文并对外发布**。区别不在"有没有输入框"，而在**输入的是自由创作还是结构化字段**。

**要做的改造**（按优先级）：

| 优先级 | 改造                                       | 做法                                                                                                                                                                     |
| --- | ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0  | **删掉打卡页全部自由文字输入**                        | 「描述」「20 字补充」「临时名字」「地点名称」四处输入框**全部删除**；改为**预设枚举**：行为多选标签 + 外观特征多选标签 + 毛色/花纹 picker + 数量 picker。想加维度只能加枚举项，**不得加回 input/textarea**                                       |
| P0  | **可见性由超管在控制台统一配置**                       | 打卡页**不提供任何公开发布入口**。策略存 `schools.sightingPublic`（默认 false = 仅社团内部可见），仅超管可在控制台开关（`setSightingVisibilityPolicy`，role=admin）。记录落库时按策略写 `visibility`，打卡者传 `public` **一律忽略** |
| P0  | **对外只暴露聚合的结构化字段**                        | `listSightings` 对非成员只返回 health/behaviors/features/count 等枚举值，**不下发 photos（用户图片）、reporter（身份）**，点位做模糊                                                                   |
| P1  | **分享边界锁定**                               | 只保留「首页/猫谱/地图/档案/积分/成员/资金/任务/TNR」等**官方信息页**的分享；打卡、建档、TNR 编辑等 **UGC 承载页一律不接分享**（审核文案里的「记录、**分享**」正是这条）                                                                   |
| P1  | 打卡照片仅用于**核实身份**，不进入公开图库                  | 前端文案同步改（去掉"也用于图鉴"这类暗示公开传播的表述）                                                                                                                                          |
| P1  | **演示/测试数据不得含自由文本**                       | `seedDemoData` 的猫档案**删除叙述性 `note`**（"饭点准时出现，亲人可摸"这类），改为结构化 `behaviors` 标签；后台列表**不展示提交人身份**                                                                             |
| P2  | `cat-edit` 的「备注」改为结构化字段（花色/性别/年龄/健康状况枚举） | 保留极短补充                                                                                                                                                                 |

> **⚠️ 2026-10-16 二审追加**：可见性开关从**打卡页**移到了**控制台**（超管专属）。  
> 这一步很关键 —— 开关放在用户侧，等于产品**提供**了"一键公开到校园"的发布能力；  
> 放在管理端且默认关闭，产品形态就是「社团内部登记 + 管理员决定是否公示」，  
> **用户端不存在任何"发布"入口**。这才是审核关注的"功能是否提供公开发布能力"。  
> 另：演示/测试数据也是审核可见的内容，同样按此口径清理。

**改造后的自我描述**（提审时填的简介/审核备注）：

> 本小程序为校园流浪猫**信息查询与登记工具**，提供猫只档案查询、地图点位、TNR 记录与资金公示。  
> 用户可提交猫只状况的**结构化登记信息**（下拉/标签选择的健康状态、行为、外观特征、投喂记录），  
> **所有用户输入均为预设选项，不提供任何自由文本创作入口**；  
> 记录**默认仅社团成员可见**，是否对访客公开由社团管理员统一配置；  
> **不提供公开发布、评论、互动等社交功能**。

---

### 路线 B：删除 UGC 功能，做纯查询工具（**最稳但伤产品**）

把打卡、建档、任务、TNR 编辑等所有"用户输入"入口从提交版本**暂时下线**，只留：  
猫谱查询、地图点位、猫详情、资金公示（管理员后台维护数据）。

- ✅ 过审概率最高，审核员挑不出东西
- ❌ 小程序变成"只读"，志愿者无法贡献数据，产品价值大打折扣
- 适合：**急着上线拿一个可用版本**，后续再逐步加回

---

### 路线 C：换企业主体（**根治，但要成本**）

个人主体拿不到社交类目，企业主体可以。需要：

- 营业执照（个体工商户即可，成本几百元，办理约 3-5 工作日）
- 主体验证（对公打款或法人扫码）
- 类目可增选「社交 - 笔记」+「工具 - 信息查询」
- ✅ 一劳永逸，不用削产品
- ❌ 需要注册主体、重新备案（备案主体变更）、迁移成本

> **注意**：如果近期本来就打算做**虚拟支付/募捐**（项目里有 `lib/vpay.js`），那本来就必须企业/组织主体 ——  
> 那么路线 C 反而是迟早要走的，不如一次到位。个人主体**无法开通微信支付**。

---

## 三、推荐执行顺序

```
第 1 步：立刻做路线 A 的 P0 改造（删自由文本 + 收紧可见性）   ← 本仓库已开始实施
第 2 步：重新提审，类目保持「工具-信息查询」
第 3 步：若仍被拒 → 退到路线 B（先把 UGC 入口整体下线，保过审）
第 4 步：并行评估路线 C（尤其如果要做支付/募捐）
```

**关于「我不接受，存在误判」**：不建议点这个。  
申诉需要论证"我的功能不属于社交-笔记"，但**打卡页确实有自由文字 + 图片 + 公开可见**，  
论证不成立，反而会浪费时间且可能留下申诉记录。**改功能比争定义快得多。**

## 四、提审时的「审核备注」怎么写（很重要）

审核员是人工看页面，**备注会显著影响判定**。建议在小程序后台提交审核时的「功能页面说明」里写：

> **【功能说明】**
>
> 1. 本小程序为**校园流浪猫信息登记与查询工具**，服务于校园动物保护社团的日常管理。
> 2. 猫只档案、TNR 记录、资金公示等均**由社团管理员维护**，普通用户仅可查询浏览。
> 3. 用户可提交**结构化的猫况登记**（健康状态、投喂与否、所在点位），  
>    数据用于社团内部核实与统计，**不对外公开发布，无评论、点赞、关注等社交互动功能**。
> 4. 照片仅用于猫只身份核实（花色比对），不作公开展示。
> 5. 本小程序**不含任何 AI 生成、深度合成功能**；猫只识别为本地特征比对，用于辅助人工核对。

**措辞要点**：

- 反复强调「**登记**」「**查询**」「**核实**」「**统计**」——工具类动词
- 明确否认「发布」「公开」「互动」——社交类动词
- 主动否认 AI（避免触发深度合成审查）

## 五、代码侧已做的改造（本次提交）

**小程序端**

- `pages/sighting-post/`：删除**全部自由文本输入**（`textarea` 描述、20 字 `input` 补充、  
  「地点名称」input、「临时名字」input、数量 `input`）；改为**预设枚举**：  
  `behaviorOptions` 行为多选、`featureOptions` 外观特征多选、`patternOptions` 毛色 picker、  
  `countOptions` 数量 picker；位置改由微信「选择位置」返回结构化名称。
- `pages/sighting-post/`：新增「**可见性**」只读说明卡（告知当前口径，**不提供开关**）。
- `pages/admin/`（**控制台**）：新增「**打卡记录可见性**」策略卡片 + 开关，  
  仅超管可操作；开启前弹窗提示"这会构成用户内容对外发布，可能被判定为社交类目"。  
  同时**移除后台列表里的"上报人"展示**（UGC 作者身份不该出现在界面）。
- `utils/const.js`：新增 `SIGHT_BEHAVIOR`（8 项）、`SIGHT_FEATURE`（10 项）枚举。
- `utils/util.js`：新增 `sightTags()` / `sightTagText()` —— 把枚举值翻成中文标签串，  
  替代原来 `item.note` 的展示位（列表页要"有信息量"但不能再是用户文字）。
- 列表渲染位替换：`cats` / `index` / `map` / `mine` / `admin` / `cat-detail` 六处  
  `wx:if="{{item.note}}"` → `wx:if="{{item.tagText}}"`。

**云端**

- `cloudfunctions/catcampus/index.js`：
  - 新增 `SIGHT_FEATURE_VALUES` 白名单（与前端逐值对齐）；
  - `addSighting` 落库 `features` + `visibility`（**由校区策略决定**），  
    删除 `note` 写入；新猫占位名由服务端按 `PATTERN_LABELS[pattern]` 生成  
    （如「未命名·橘猫」），**不再接受用户 `catName`**；
  - 新增 `sightingPolicyPublic(schoolId)` + action `setSightingVisibilityPolicy`（role=admin）；
  - `listSightings`：非成员只查 `visibility === 'public'`，本人 `mine:true` 不受限；
  - `getOverview` 首页最近目击同样过滤非公开记录；
  - `updateSighting`：删除 `note` 写入分支（UGC 文字后门），  
    `behaviors`/`features` 允许本人改，`public` **仅超管可改**；
  - `seedDemoData`：删除演示猫档案的叙述性 `note`，改为结构化 `behaviors`，  
    `note`/`internalNote`/`medicalNote` 一律置空（**审核在测试账号里看得到**）。
- `cloudfunctions/catcampus/lib/core.js`：`sanitizeSighting` 加严 ——  
  非成员、非本人、且 `visibility !== 'public'` 的记录**返回 `null`**（调用方 `filter(Boolean)` 剔除）；  
  公开记录仍删除 `photos` / `reporter` / `reporterName` 并做点位模糊。
- `cloudfunctions/catcampus/lib/security.js`：`assertSightingSafe` 改为对  
  遗留文本字段（`note`/`catName`/`locationName`）联合检测，兼容老客户端。

**测试**

- `scripts/test_compliance_ugc.js`：扩到 **93 项**（新增控制台策略、打卡页无开关、  
  演示数据合规、features 对齐、云端约束等）；
- `scripts/_cf_test.cjs`：扩到 **97 项**（新增策略开/关、打卡者传 public 无效、  
  普通用户不能改策略、旧记录不追溯、features 白名单、服务端占位名）。

## 六、给用户的结论

**这次不是误判，是产品形态真的命中了社交类目。** 三条路里：

- **想尽快上线** → 走路线 A（已开始改造），一次不行就退到 B
- **想不削产品** → 走路线 C 注册个体工商户
- **别点「我不接受，存在误判」** —— 理由不成立，纯浪费时间

另外提醒：项目里已有**虚拟支付**模块（`lib/vpay.js`），个人主体**开不了微信支付**。  
如果募捐/支付是产品规划的一部分，企业主体是早晚要办的，可以直接规划路线 C。
