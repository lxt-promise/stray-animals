# 积分值与猫粮值规则（实现说明）

> 对应 `规则.txt` V1.0。本文记录**代码里实际怎么实现的**，以及规则文档留白处
> 做的具体决定 —— 改数值时看这一份就够，不用翻代码。

---

## 一、为什么必须拆成两套账

| | 积分值 `users.points` | 猫粮值 `users.food` |
|---|---|---|
| 定位 | 经验 / 等级 | 流通货币 |
| 变动 | **只增不减** | 可增可减，下限 0 |
| 每日上限 | 150 | 50（礼包 / 升级奖励不计入） |
| 用途 | 判等级、发称号 | 识别服务等消费 |
| 消费影响 | — | **不影响积分和等级** |

早期只有一个 `users.points`，前端叫「猫粮值」。一旦识别要扣费，这个数字就会减少，
而它同时又是等级依据 —— **花猫粮等于掉级**，与规则直接冲突。所以拆成两个字段、
两套日计数（`pointsDay/pointsToday` 与 `foodDay/foodToday`）、两本流水（用 `currency` 区分）。

## 二、积分值（只增不减）

| 行为 | 积分 | 流水 kind |
|---|---|---|
| 每日打卡 | +5 | `daily` |
| 投喂干粮 | +2 | `feedDry` |
| 投喂零食 / 猫条 | +3 | `feedSnack` |
| 投喂罐头 / 湿粮 | +4 | `feedWet` |
| 投喂自制餐 | +5 | `feedHomemade` |
| 图鉴点亮新品种（每品种一次） | +10 | `dexNew` |
| 人工确认识别结果 | +2 | `confirm` |

- **每日上限 150**，超出部分静默截断（返回 `capped: true`，前端提示今日已满）。
- 投喂只在「本人投喂」时发放；食物类型走**白名单**，非法值回落 `dry`（+2）。
- 图鉴按 `catSeen` 去重：打卡「首次遇见」与识别「确认」共用同一份判断，
  同一只猫只会点亮一次。

### 等级表

| 等级 | 称号 | 积分区间 |
|---|---|---|
| Lv.1 | 猫语新手 | 0 – 99 |
| Lv.2 | 爱猫人士 | 100 – 499 |
| Lv.3 | 猫界达人 | 500 – 999 |
| Lv.4 | 资深铲屎官 | 1000 – 2999 |
| Lv.5 | 喵星守护者 | 3000 – 4999 |
| Lv.6 | 传奇喵侠 | 5000+ |

- 区间**左闭右开**。规则原表 `0–100` 与 `100–500` 共享 100，取靠后一档
  （刚到 100 就升 Lv.2），否则 100 分同时属于两级。
- **只升不降**：判级读 `users.peakPoints`（历史最高积分），不读当前积分。
  删除记录、管理员调账都不会导致掉级。
- 升级奖励 **+50 猫粮/级**，跨级按级差补发（1→3 级 = 100），**不占**当日 50 上限。

## 三、猫粮值（可增可减）

| 来源 | 猫粮 | 流水 kind | 占日上限 |
|---|---|---|---|
| 新手礼包 | +50 | `gift` | ❌ 一次性 |
| 每日打卡 | +5 | `daily` | ✅ |
| 建立档案（无照片） | +15 | `catCreate` | ✅ |
| 建立档案（含照片） | +20 | `catCreatePhoto` | ✅ |
| 升级奖励 | +50/级 | `upgrade` | ❌ |
| 参与 TNR | +50 | `tnrHelp` | ✅ |
| 人工确认识别 | — | — | 不发猫粮 |

- **每日上限 50**。建档、打卡、TNR 共用这一个额度，超出截断。
- 新手礼包在**首次登录时自动发放**，用 `users.giftAt` 做「只发一次」的条件更新抢占。
- 建档奖励发给**建档的管理员**（`saveCat` 是 admin 权限）。

### 消耗

| 项目 | 价格 | 说明 |
|---|---|---|
| 猫咪识别服务 | 20 猫粮/次 | **首次免费**（`users.freeRecognizeAt` 为空时） |
| 每日识别次数 | 最多 10 次 | `users.recognizeDay/recognizeToday` |

- 扣费在 `vision.start()` 里、**建任务之后**执行：任务 id 当流水幂等键；
  扣费失败（余额不足 / 次数用完）会把刚建的任务删掉，避免留下「不花钱的空任务」被轮询白跑。
- 顺序上先判次数再判余额：次数用完时提示「今天次数用完」比「猫粮不足」更贴近实际处境。
- 前端 `recognize` 页在**选素材之前**就展示价格与剩余次数，余额不足直接引导去「我的」。

### 超级管理员礼遇

超管账号首次登录时由 `points.grantAdminPrivilege()` 一次性置为**满级账户**：`points = peakPoints = 5000`（Lv.6 传奇喵侠）、`food = 500`。

几个刻意的选择：

- **一次性，不是每次登录刷新**。写 `adminGrantAt` 标记位后不再发放。否则会凭空多出无数条
  `adminGift` 流水，账本与实况对不上（一笔钱只能发一次，这是账务问题，不是体验问题）。
- **取 max 而不是覆盖**。超管自己打卡攒的积分/猫粮不该被抹掉。
- **失败不阻断登录**。这是登录链路上的附加权益，发不出去最多下次登录再补；登录失败才是灾难。
- **写两条 `adminGift` 流水**（积分 +5000 / 猫粮 +500），保证账实相符、可审计。

#### 超管免消耗（2026-10-24）

超管**任何消耗猫粮的功能都不扣猫粮**，识别也**不占每日次数**：

| 位置 | 普通用户 | 超级管理员 |
| --- | --- | --- |
| `spendFood()` | 余额不足抛 402 | `spent: 0, waived: true`，余额不动 |
| `chargeRecognize()` | 首次免费 → 20/次 → 日 10 次（429/402） | `cost: 0, waived: true`，不推进日计数 |
| 流水 | `delta: -20` | `delta: 0`，`reason` 追加「·超管免消耗」 |

几个实现要点：

- **豁免判断必须在余额/次数校验之前**。放在后面等于没做 —— 余额 0 的超管照样被 402 拦下。
- **仍写一条 `delta: 0` 的流水**。猫粮值是审计信息，超管哪天用过什么功能应该查得到；
  `delta: 0` 既如实（没花钱）又不污染余额，也不占日上限。
- **`summary()` 下发 `waived`**，前端据此放行（`recognize.ensureBillable()` 见 `waived` 直接返回 true）。
  前端无从判断超管身份 —— 那要看云函数环境变量里的 `SUPER_ADMIN_OPENIDS` 白名单。
- 前端计费条文案改为「超级管理员免消耗 · 不限次数」。

## 四、规则文档留白处的决定

| 项目 | 决定 | 理由 |
|---|---|---|
| **食物类型分档**（文档写「见下表」但无表） | 干粮 +2 / 零食 +3 / 罐头 +4 / 自制 +5 | 按投喂成本递增，恰好落在 +2~+5 区间 |
| **建立档案 15~20 的取值** | 无照片 15、有照片 20 | 照片是这只猫能进特征库被识别出来的前提，多给 5 点 |
| **TNR 奖励**（文档未列） | 猫粮 +50，占日上限 | TNR 是重投入（送医、术后护理），去掉奖励会让功能失去激励；占上限防止刷 |
| **人工确认**（文档未列） | 积分 +2，不发猫粮 | 人机协同需要小额激励；猫粮渠道严格按文档只保留 4 项 |
| **删除打卡记录** | **不退积分，只退猫粮** | 积分只增不减；若删记录扣积分，用户为保等级只能留着错记录 |
| **上报新猫**（打卡时） | 不发奖 | 打卡上报只落 pending 记录，还没产生档案；奖励统一在建档时发 |

## 五、老数据迁移

`users.points` 的语义从「猫粮余额」变成「积分值」，**数值不动**：

- 老用户的 `points` 直接作为积分（只增不减，作等级依据是安全的），`peakPoints` 默认等于它。
- `food` 从 0 起算，登录时 `claimGift` 补发新手礼包 50，保证升级后第一次进来就能完整体验一次识别。
- 老流水（无 `currency` 字段）读取时统一按 `point` 归档，前端标签显示「积分」。
- `backfillPoints` 迁移的历史期初行显式写 `currency: 'point'`。

### 页面分工

| 页面 / 入口 | 展示什么 | 为什么 |
|---|---|---|
| 我的 → 三格统计 | **猫粮值、打卡次数、图鉴数** | 个人主页要的是「我攒了多少、拍了多少、认识多少只」，不摆账本 |
| 我的 → 图鉴收集 | 只显示「已收集 / 本校总数」，点击进图鉴页 | 进度墙与解锁细节是独立一屏（见 `docs/图鉴与学校绑定.md`）|
| 我的 → 等级标签（头像旁） | `Lv.N 称号`，点击进「等级页」 | 称号是身份标识；积分与进度属于等级页，点进去看 |
| 我的 → 猫粮明细 | 只看 `currency='food'` 的流水 | 混排时「-20」会被误读成「等级被扣了」 |
| 我的 → 规则说明 | 点击展开规则正文（原来常驻页底） | 常驻占屏且没人看；放到「意见反馈」上方，需要时再看 |
| 等级页（`points?type=point`） | **只显示积分总值 + 等级徽章 + 进度 + 阶梯，不列流水** | 积分只增不减、唯一用途是判等级，「我现在多少分、差多少升级」就是全部信息；不查流水也就少一次读、少一段渲染 |
| 等级页右上角「规则说明」 | 点击展开同一份规则文案 | 看等级时最想确认「怎么升」，就地展开比退回「我的」更顺 |

### 三格统计的点击去向

三格都能点，因为「我攒了多少 / 拍了多少 / 认识多少只」这三件事都有自己的下一页：

| 卡片 | 去哪 | 实现 |
|---|---|---|
| 猫粮值 | 猫粮明细（`points?type=food`） | `mine.js: goFoodDetail()` |
| 打卡次数 | 猫谱 → 「打卡记录」tab（本人过滤 `mine:true`） | `mine.js: goCatsSighting()`（tabBar 页只能 `switchTab`） |
| 图鉴数 | 图鉴收集页（`pages/dex`） | `mine.js: goDex()` |

标签后面跟一个 `›`，是唯一的「可点」暗示 —— 没有它没人会去点卡片。

### 打卡次数为什么会出现负数（-2）

`users.sightingCount` 是**派生计数**，不是账本。原 `deleteSighting` 无条件给**操作者**
`_.inc(-1)`，而后台「打卡记录」列表允许超管删除任意人的记录：

```
超管删掉 2 条别人的打卡  →  记录作者 +0（本该 -2），超管自己 -2
```

所以出现 -2 的几乎一定是**管理员账号**，且删的条数 = 负了多少。
（本人删自己的记录是平衡的，不会出现负数。）

修法三处，缺一处就还会出现：

1. `deleteSighting` 回退**记录作者**（`s.reporter`），不是操作者；超管删别人的不动自己。
2. 回退用条件更新 `where({_id, sightingCount: _.gt(0)})` —— 并发或脏数据下永远减不到负数。
   记录作者找不到档案（历史/种子数据）则谁都不减。
3. `login` 兜底自愈：`repairSightingCount()` 发现为负就 `count()` 重算真实条数写回。
   **只在负数时触发**，正常用户不多付一次查询。派生值重算比「+2 补回来」可靠：
   补数要求你知道少减了几次。

前端再夹一层 `Math.max(0, Number(x) || 0)`，避免云端还没部署新版本时把 -2 显示出来。

### 为什么前端也有一份等级表

等级文案曾经是「云端下发 `level` 对象、前端拼字符串」。云端少下发一个字段
（云函数还是旧版本、字段改名、对象被裁剪），界面就会原样渲染成
`0 / undefined 分`、`距 Lv.undefined undefined 还差 undefined 分` —— 不报错、不白屏，
只是数字全没了，最难被发现。

现在分工是：**云端只给数据**（`points` / `peakPoints` / `food`），
等级、进度、下一档距离全部由 `miniprogram/utils/level.js` 算，云端返回什么形状都不影响展示。
代价是等级表出现两份，用 `scripts/test_points_level.js` 的 S10 逐值比对 + 13 个边界点
一致性 + 「文案永不出现 undefined」三条断言锁住。

## 七、改数值时注意

1. **四个地方要同时改**：`lib/points.js` 的奖励表、`utils/const.js` 的 `RULES`（「我的」与等级页共用）、
   `points.js` 的 `MODES` 文案、`const.js` 的 `FOOD_TYPE` 标签分值。
   测试会卡住「前后端枚举不一致」，但卡不住文案数字。
2. 改等级门槛要**同时改两份** `LEVELS`：云端 `lib/level.js` 与前端 `utils/level.js`。
   `test_points_level.js` 会逐值比对，改漏一处直接红。
3. 改识别价格只改 `points.js` 的 `RECOGNIZE_COST`；前端价格来自 `pointsSummary`，不会漂移。
4. 改超管礼遇额度只改 `points.js` 的 `ADMIN_FOOD` 与 `level.LEVELS` 末档门槛。
   已经发过礼遇的账号（有 `adminGrantAt`）不会重发 —— 要重发得手工清掉该字段。
