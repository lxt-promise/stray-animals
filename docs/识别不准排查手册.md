# 识别不准 / 结果不一致 排查手册

> 2026-10-17 整理。现场症状：「上传白猫和橘猫都识别成小黑」「有时有毛色/花纹/体型/置信度，
> 有时只有检测/帧数」。
> 结论：这两个症状**不是同一个 bug**，但都源自「识别链路会在失败时静默换一条路，而换出来的
> 结果长得和真结果一样」。

---

## 一、先看懂界面上那两张卡

### 情况 A：有「品种 / 毛色 / 花纹 / 检测 / 帧数」（2026-10-17 之后的正常形态）

```
识别特征
  品种    橘狸花
  毛色    橘猫
  花纹    虎斑条纹
  检测    整图（未裁剪）
  帧数    1
```

品种/毛色/花纹现在**恒可用**：识别服务里有两层，CLIP 没装就走
`app/attrs.py` 的纯 numpy 色域分析（零额外依赖、单图 ~5ms）。

`检测 = 整图（未裁剪）` 仍然是**准确率低的第一物理原因** —— 没启用猫体检测模型
（`DETECT_ONNX` 为空），整张图直接喂给 ReID，背景（瓷砖、地板、床单）会进入
特征向量，不同猫被背景拉近、同一只猫换个地方就认不出。属性不妨碍匹配，
但检测这一步是**决定性的**。

### 情况 A2：只有「检测 / 帧数」，没有花色

说明花色**判不出来**，下面是原因（服务端 `meta.attrReason` 直接下发）：

```
识别特征
  检测    整图（未裁剪）
  帧数    1
这次没能判断出毛色和花纹，换一张更清楚的正面照再试。
```

常见具体原因：

| `attrReason` | 含义 | 怎么做 |
| --- | --- | --- |
| 画面里猫体区域不足（有效占比 12%，需 22%） | 猫太小 / 被遮挡 / 背景占比过高 | 拍近一点，或配 `DETECT_ONNX` 先裁出猫体 |
| 颜色不集中（最大色占比 9%） | 花色太杂、或整图是背景 | 同上 |
| 图片太小（4x4） | 素材本身有问题 | 检查上传链路 |

**这是有意的"不给假数据"**：有效猫色区域不够时返回空 + 原因，绝不硬编一个
看起来合理的颜色。伪造属性比没有属性危害大 —— 用户会当真，还会拿它去回填档案。

### 情况 B：有「毛色 / 花纹 / 体型 / 置信度」（旧版截图，已修）

```
识别特征
  毛色    橘色
  花纹    white
  体型    健壮
  置信度  65%
```

**这是旧版本地占位引擎的输出，不是识别结果。**

旧版 `vision.localFeatures()` 按 fileId 哈希随机 pick 出这四个值，返回的 tags 和真模型
输出格式完全一致，前端无从分辨。也就是说：

- 「体型 健壮」「置信度 65%」是**随机数**；
- 「花纹 white」恰好撞上档案里「小白」的 pattern，于是展示成「匹配候选 小白 56%」——
  **这不是识别，是随机数 + 文本匹配**。

> 2026-10-17 已修：本地降级不再生成任何属性，`result.degraded = true`，
> 前端换成「识别服务暂时不可用」卡片，不再展示候选。
> 看到这种四行形态说明**客户端还是旧版本**，重新编译上传即可。

## 二、为什么会降级到本地引擎

云函数侧的判断链：

```
同步调用 recognize（客户端 ~3s 预算）
  → AI 窗口只有 1800ms（AI_POLL_CAP_MS）
      → 自建服务响应 > 1800ms → 超时
          → 重试 MAX_AI_ATTEMPTS 次
              → 仍失败 → provider='local'（占位引擎）
```

所以**只要自建服务慢于 1.8 秒，就一定会降级**。而现场日志里出现过
`latency 19887ms` / `78109ms` 的响应 —— 78 秒，必然降级。

### 78 秒花在哪（已定位 + 已修）

旧版 `/v1/recognize` 在检索**之前**同步做增量补库：

```python
ensure_index(req.cats, req.schoolId)   # limit=40，每只猫下载一张照片，单次下载超时 15s
```

一次请求顺手补十几只猫 = 十几次图片下载 + 十几次推理，响应被拖到几十秒。

现在改为：

- 只处理**本次真带了照片**的猫（云函数只给待入库的猫带照片）；
- 最多补 **2 只**（`BOOTSTRAP_LIMIT`）；
- 最多花 **1200ms**（`BOOTSTRAP_BUDGET_MS`），超了立刻收工，下次接着补（幂等）。

请求日志会打出分段耗时，一眼定位：

```
/v1/recognize 1420ms（补库2/1180ms 推理210ms 检索1ms 帧1 候选3 库12）
```

## 三、为什么候选只有一只、而且分数是 0

`search()` 旧版对全库排序后**直接取 Top-N，没有任何阈值**。

特征库里只有 1 只猫时，无论上传什么都返回它 —— 白猫 → 「小黑 0%，特征相似度 48.7%」。
48.7% 属于"完全无关"区间（不同猫 0.75~0.93，无关图 0.51~0.55），本该被挡掉。

现在：相似度低于 `MIN_SIM`（默认 **0.62**）的候选**直接丢弃**，一个都不剩时前端显示
「档案库里没有它」，而不是给一个 0 分的 Top1。

> 顺带修了一个语义 bug：`ensure_index(skip_ids={req.cats[0].id})` 里的 `cats[0]`
> 是**全库第一只猫**，跟本次上传的照片毫无关系 —— 结果全库第一只猫永远补不进库。

### 为什么特征库会缺猫

旧版 `markIndexed()` 只要 `/v1/recognize` 返回 200，就把**所有**待补库的猫标成
`aiIndexAt = now`。但服务端补库可能一只都没建成（照片下载失败 / 维度不符 / COS 写失败）。
被误标的猫从此不再送照片，向量永久缺失 —— 线上表现就是「档案 4 只猫，识别只认得 1 只」。

现在：

1. 只有服务端在 `meta.indexedIds` 里**确认**的猫才记账；
2. 每轮识别拿 `indexedIds` 对一遍，`aiIndexAt` 有值但库里没有的 → **自动重置**，
   下一轮重新送照片。存量脏数据无需人工修。

## 四、自检：一条命令定位问题

### 先说最省事的：超管后台里直接看

「我的 → 管理后台 → 特征库（花色比对）」现在有一块体检卡片：

```
档案 12     已录入 8     未录入 4

大橘    橘猫 · 3 张照    [录入]
小白    纯白 · 0 张照    [无照片]
```

- 三个数字分别是档案数、特征库里真有向量的、没录入的。
- 未录入的猫按「照片多的优先」排在前面，点「录入」当场补建（force 重算，8 秒超时）。
- 「无照片」是灰的：没有档案照就建不了库，先去档案里加照片。
- 顶部「刷新」重新拉一次。

**数据从哪来**：查识别服务 `GET /v1/index/ids` 拿真实 id 列表，和档案逐个对。
**不查云库的 `aiIndexAt`** —— 那只是乐观记账，服务端补库失败的猫照样带「已入库」标记。
识别服务连不上时卡片会标注「按本地记录推测，未核实」，此时别把它当结论。

它上面还有一块**「识别引擎」**卡片，三行直接对应「识别不准」的三大成因：

```
猫体检测    已启用    yolov8n.onnx
花色识别    本地色域  数像素推算，够用
特征库      8 只     sqlite
```

这块存在的唯一理由：**「YOLO 没配」和「配了但没加载上」在用户侧表现完全一样**
（都是识别不准），日志里也只是一条 warning。改完配置点一下「刷新」就能确认生没生效，
不用 SSH 上去 curl。识别服务连不上时它照实显示错误，不会显示一份"看起来正常"的默认值。

### 再看服务本身

```bash
curl -H "Authorization: Bearer $API_TOKEN" https://<你的服务>/health
```

```json
{
  "ok": true,
  "provider": "onnx",
  "dim": 768,
  "size": 224,
  "detector": false,     // ← false = 整图提特征，背景污染，准确率明显下降
  "attrs": false,        // ← false = 没有毛色/花纹（只影响展示）
  "minSim": 0.67,
  "indexed": 1,          // ← 特征库里只有 1 只猫！识别必然只返回它
  "indexBackend": "cos"
}
```

三个字段对应三大成因：

| 字段 | 期望 | 不对时怎么办 |
|---|---|---|
| `indexed` | ≈ 档案里猫的总数 | 差很多 → 跑 `/v1/index/build`（`force=true`）重建；确认 `INDEX_BACKEND=cos`（sqlite 在云托管会随容器重建归零） |
| `detector` | `true` | 配 `DETECT_ONNX`（YOLO 猫体检测模型） |
| `attrs` | 视需求 | 想显示毛色/花纹才需要 `USE_CLIP=1`（多几百 MB + 每帧约 200ms） |

## 五、部署侧必须做的一件事：云函数超时

现场报错：

```
Error: errCode: -504003 | errMsg: Invoking task timed out after 3 seconds
FUNCTIONS_TIME_LIMIT_EXCEEDED
```

这是**云函数执行被平台在 3 秒处掐断**，不是客户端等待超时。

同步路径的设计预算 `SYNC_BUDGET_MS = 12000`（预留 1.5s 后实际 10.5s），
只有平台超时 ≥ 15s 才跑得完。**默认 3s 的话，同步路径每次都会被掐**，
客户端收到 `-504003` 后转轮询 —— 功能不坏（任务状态已落库、可续跑），
但每次都多一轮等待，体验差。

操作：云开发控制台 → 云函数 `catcampus` → 配置 → **超时时间改为 20 秒**。

> 代码侧已经保证「被掐也不丢进度」：每步产物都先落库，轮询从断点接续。
> 但把超时调大是让它一把出结果的唯一办法。

## 六、准确率本身还能怎么提

按性价比排序：

1. **猫体检测模型**（`DETECT_ONNX`）—— 影响最大，**已内置并默认启用**。
   整图提特征时背景占主导权重，裁出猫体后类内/类间间隔会明显拉开。
   若 `/health` 的 `detector` 是 `false`，说明模型没找到（`detectModel` 会是空串）。
2. **保证特征库完整**（`indexed` ≈ 档案数）。库里缺猫时，"识别"必然变成"找不到"。
3. **把人工确认的样本并入特征库**（超管后台「确认样本」卡）—— 见下面第六之二节。
   档案照是摆拍的正脸，用户识别时拍的是远处/侧身/逆光；**分布不一致**才是
   「明明是同一只却只有 68%」的主因，补这个比补张数更对症。
4. **建档照片质量**——每只猫 3~6 张、正/侧面都有、光线不同，`/v1/index/build` 会合成代表向量。
5. **调 `MIN_SIM`** —— 如果真实同猫的相似度分布偏低（看日志 `rawSim`），
   可以下调到 0.58；但低于 0.55 会重新引入噪声候选（无关图上限约 0.55）。
6. 属性识别（CLIP）只影响展示，**不要为了它牺牲推理速度**。CLIP 没装也没关系，
   现在有色域分析兜底（`ATTR_CONF_MIN` 以下自动接管）。

### 六之二、每只猫该用几张图建库（阈值怎么定的）

| 参数 | 值 | 位置 |
|---|---|---|
| 单只猫视图上限 | **8** | `vision.js` → `INDEX_PHOTOS` |
| 建档后自动入库 | **5** | `vision.js` → `INDEX_PHOTOS_AUTO` |
| 确认样本每猫上限 | **3** | `vision.js` → `SAMPLE_PHOTOS_PER_CAT` |
| 样本最低匹配分 | **45**（= 匹配线） | `vision.js` → `SAMPLE_MIN_SCORE` |
| 代表向量内点比例 | 0.7 | `server/app/config.py` → `REP_KEEP` |
| 视图离散度门槛 | **0.88**（低于此值只用 medoid） | `server/app/config.py` → `REP_SPREAD_MIN` |

> ⚠️ `REP_KEEP=0.7` 只在 **n≥4** 时才真的剔除（`ceil(3×0.7)=3`，三张等于不剔）。
> 照片少时靠 `REP_SPREAD_MIN` 这条兜底：视图散得开就不平均，直接用 medoid。
> 依据见 `docs/特征库单向量与多向量实测.md`。

**为什么是 8：**

- 收益递减很明显。1→3 张提升最大（覆盖正脸 / 侧脸 / 逆光三种常态），
  3→8 张继续小幅提升，**超过 8 张基本不再涨**。
- 服务端 `rep_vector` 只保留 `ceil(n×0.7)` 条内点：n=8 取 6 条，medoid 已经稳定；
  再多只是把同一批内点多平均几遍。
- 成本线性：每张图下载 + 编码约 400~600ms，8 张 ≈ 4 秒/只。
  这直接决定了「一次云函数调用能建几只猫」（样本建库按 3 只/批推进）。
- 张数过多的副作用：相册里混进「拍糊了 / 拍的是旁边另一只猫」的概率随张数上升，
  medoid 能扛 1~2 张离群点，扛不住一堆。

**为什么自动入库只用 5 张**：那条路径挂在「保存档案」的主流程上，硬预算 2.2s，
带 8 张必然超时，而超时 = 一只都没建成。剩下的交给后台「用确认样本建库」补齐。

**确认样本为什么只给 3 张**：样本是补充不是主体，档案照的正脸才是门面；
3 张足够覆盖「远处 / 侧身 / 逆光」这些查询态，再多会稀释代表向量。

**分数门槛为什么等于匹配线**：低于匹配线意味着服务端自己都判「没认出来」，
此时用户的确认很可能是认错猫 —— 把别的猫的照片写进这只猫的特征库，比不建库更糟。
老样本没有 `score` 字段（按 0 处理），需要管理员在后台「指定猫」或用旧数据重认一次。

## 七、2026-10-24 那次「同一只猫只有 9%」：映射问题，不是检索问题

现场：上传**档案里那只橘猫**的另一张照片，排序是对的（橘猫 76.3% > 小奶牛 69.8%），
但界面上写的是「匹配候选 橘猫 **9%**」，而且判定「没认出来」。

### 根因是映射，不是检索

旧版把余弦**线性**压成展示分：`(sim - 0.75) / (0.90 - 0.75) * 100`。
0.763 落在窗口起点上 → 9 分；`IDENTIFY_MIN=50` 又要求余弦 ≥ 0.825 才算「认出来」。
两个数字一起把一次**正确的匹配**判死了。

那对 0.75/0.90 是「同一张照片做旋转/翻转」测出来的（0.96~0.996），
而真实场景是「同一只猫、另一张照片、另一个背景、另一束光」——

```
tools 实测（8 张真实照片，东南大学猫）：
 同一只猫的不同照片 : 0.687 ~ 0.761（均值 0.724）
 不同猫之间         : 0.55  ~ 0.781（均值 0.644）
```

两坨是**重叠**的。任何硬边界都会把一部分真匹配判死，这是线性窗口的根因性缺陷。

### 现在怎么算的

```
score = 99 / (1 + exp(-(余弦 - SIM_MID) * SIM_SLOPE))     # SIM_MID=0.755, SIM_SLOPE=30
余弦 0.62→1   0.70→16   0.74→39   0.763→55   0.80→79   0.85→94   0.90→98
```

- 单调、无死区：分数可以低，但**不会再有「0 分」的真匹配**；
- `IDENTIFY_MIN` 跟着改成 **45**（≈ 余弦 0.745），云函数 `LOW_CONF` 同步 45；
- Top1 多一行「领先次名 x.x%」——排第一说明什么，和「有多像」是两个问题；
- Top1 与次名差 < `GAP_CLEAR`(0.05) 时打折，但地板是 `GAP_FLOOR`(0.75)，
  旧值 0.5 会把 56 分砍到 28 分，反而更像「没识别出来」。

### 同时改了一处「多照片合成」

`build()` 原来对档案里的照片做**裸平均**。平均值对离群点没有抵抗力：
5 张里 1 张糊的/拍错的，会把这个猫唯一的门面向量拽偏。
现在 `engine.rep_vector()` 先找 medoid（到其它向量平均相似度最高的那条），
只平均离它最近的 `ceil(n * REP_KEEP)` 条。`n ≤ 2` 时退化为平均。

### 记住这条：展示分低 ≠ 排序错

排查顺序永远是 **先看排序（`rawSim` 谁大）→ 再看展示分**。
排序对而分数低，是校准问题（改 `SIM_MID`）；
排序本身就错，才是模型/素材问题（补档案照、检查检测框、上更好的 ReID 权重）。

### 六之二・花色（属性）判不准：先查曝光，再查红色杂物（2026-10-25）

「没匹配到猫」时用户看到的品种/毛色来自本地色域分析，它有两个已修复的
系统性盲区，排查时优先核对：

1. **曝光**：色桶的分界线是绝对亮度（白/灰 175、黑 62、橘/棕 130），
   现场照片曝光差异会整桶搬家 —— 实测同一只黑白猫只改亮度，
   `white` 占比从 0（暗）涨到 0.36（亮），结论从「奶牛」跳到「纯黑」。
   已做**曝光自适应**：用 V 的 98 分位估计曝光、整体平移阈值
   （`ATTR_EXPOSURE_REF/GAIN/MAX`，`GAIN=0` 关闭）。排查入口是
   `meta.attrShift`：|shift| 频繁顶到 45 说明照片曝光严重偏离，
   结论仅供参考。诊断工具：`server/tools/attr_probe.py --grid --detect`。
2. **红色杂物**：`red` 桶（渔网/红布/砖墙）曾计入暖色总量，一张
   「白猫坐红渔网」被硬判成橘猫。2026-10-25 起 red 只在 `palette`
   里展示、不参与判定；如果某张图花色离谱，先看 `attrPalette`
   里 red 占比是否异常高。
3. **多帧一致性**：视频识别不再「取置信度最高的单帧」，改为把各帧
   色板加权平均后统一判定 + 各帧结论投票折进置信度
   （`attrs.merge_and_decide`）。`attrReason` 出现「不一致」时结论
   已被降权，前端按「仅供参考」处理。单帧置信度公式不变，单图行为不受影响。

已知未解：条纹检测（`_stripe_score`）对检测框位置敏感（框漂移会让
方向性比值跌破 1.15 直接 0 分），狸花在部分裁剪下会判成玳瑁 ——
样本量不足，暂不动阈值，靠多帧聚合缓解。

### 关于第 1 条（YOLO 检测）：到底复杂不复杂、会不会超时

**不复杂，代价是"配一下"，不是"写一套"。** `engine._Detector` 早已接进识别流程，
检测不到自动退回整图；2026-10-17 起模型随仓库发布，`DETECT_AUTO` 默认开，
**留空即自动发现 `models/yolov8n.onnx`** —— 部署时什么都不用配。

- 模型：`server/models/yolov8n.onnx`（12.8MB，COCO 80 类，class 15 = cat）。
  比 `reid.onnx` 的 90MB 小得多，`onnxruntime` 本来就是必装项，**不需要 torch / ultralytics**。
  （自己导出才要 `pip install ultralytics`，那是一次性动作，不进运行环境。）
- 关掉：`DETECT_ONNX=off` 或 `DETECT_AUTO=0`。
- 自查：`/health` 的 `detector` 应为 `true`、`detectModel` 显示 `yolov8n.onnx`；
  识别卡片的「检测」从「整图（未裁剪）」变「已定位猫体」。

**不会超时。** 本机 16 核 CPU（4 线程推理）实测，`tools/bench_detect.py` 可复测：

| 场景 | 不开检测 | 开检测 |
|---|---|---|
| 单帧 `features()` | 99ms | 172ms |
| 8 帧 `analyze_frames()` | 794ms | **924ms** |
| `/v1/recognize` 端到端 | 204ms | ~270ms |

检测本身约 58ms/张。8 帧 924ms，同步预算（`SYNC_BUDGET_MS=12000`，扣预留后 10.5s）
用了不到一成，单次轮询预算 2.4s 也占不到一半。

### 识别流程现在长这样（`engine.analyze_frames`）

```
检测（只跑一次，取中间帧；没框到再试首/尾，最多 3 次）
  ├─ 外扩 8% 的框 → 逐帧裁剪 → 提特征 → 平均 → 归一化        （DETECT_PAD）
  └─ 紧绷框      → 选花色最清楚的一帧 → 色域分析
```

四个「不做就会变差、但不会报错」的点：

1. **检测只跑一次，多帧复用同一个框**。相邻帧几乎一样，逐帧检测白花 N×58ms。
   更要紧的是：每帧各裁各的框，视野不一致（猫挪了、框抖了），**多帧平均反而更糊**。
2. **NMS 去重 + 按面积选主体**。YOLO 导出的是未后处理的原始输出，同一只猫会给十几条
   高度重叠的框（实测一张图 10 条）。不去重就按分数挑，很容易挑到同一只猫的另一个框；
   而分数最高的往往是构图里最近的小猫，不是画面主体。
3. **提特征用外扩框、数颜色用紧绷框**。外扩能补回被切掉的耳尖/尾巴（个体特征更完整），
   但每扩一圈都带进背景 —— 实测 8% 外扩把绿墙和木桌算进色域，白猫从「纯白」变成
   「颜色不集中」判不出来。两个用途诉求相反，就得用两个框。
4. **花色取置信度最高的那一帧**、不做平均。糊帧会把橘色冲淡成「灰橘」；
   花色是离散标签，跟「哪一帧看得最清楚」走才对。

### 三个历史坑（都只在配了检测后才会跑到）

| 时间 | 症状 | 根因 |
|---|---|---|
| 2026-10-15 | 线上 500，`Add node ... 257 by 1370` | crop 的 letterbox 缩放系数按**原图**算，极端长宽比下一边被缩到 1370 |
| 2026-10-17 | 不报错，但 crop 是猫的胸口 | 模型输出是 **cxcywh**，旧代码按 xyxy 读 |
| 2026-10-17 | 不报错，但框整体错位 | 逆变换用 `w/size`（拉伸系数），预处理却是 **letterbox**（缩放 + 补边） |

第二条尤其阴：640×440 的图上，旧代码把「整只猫」框成 `[283,227,363,268]` —— 一块胡须和
胸口，尺寸看着合理、位置离谱，提特征等于随机采样，**接了检测反而更差**。

回归：`server/tests/test_detector_box.py`（20 项，含真模型 + 真猫图）、
`server/tests/test_analyze_frames.py`（7 项，含「不许每帧都检测」）。

一个白捡的收益：**花色分析依赖检测框**。同一张「绿墙前的白猫」，不开检测时色域被绿墙
刷满，返回「画面里没有可用于判断花色的区域」；开了检测才判出「白猫 / 纯白 / 纯色」。

## 八、花色（品种 / 毛色 / 花纹）是怎么判的

两层，按顺序：

| 层 | 实现 | 依赖 | 何时生效 |
| --- | --- | --- | --- |
| 1 | CLIP 零样本（`USE_CLIP=1`） | torch + open_clip（+600MB） | 装了且置信度 ≥ `ATTR_CONF_MIN`（默认 0.5） |
| 2 | `server/app/attrs.py` 色域分析 | **无**（numpy + pillow） | 上面不满足时**

第 2 层做的事，说白了就是"数像素"：

1. 缩到 96×96，转 HSV，逐像素归类到 8 个色桶（白/黑/灰/橘/深棕/米黄/红棕/其他）。
2. 背景抑制：整图模式给边缘和四角**高斯降权**；检测框裁出的 crop 不降权（否则会削掉耳朵和尾巴）。
3. 条纹检测：算水平和垂直方向的**梯度能量比**。条纹是单向重复的，两方向能量拉开；
   噪点两个方向都大但相等，会被比值挡掉。
4. 组合规则：三花 = 白+黑+暖色三色共存；玳瑁 = 黑+暖色且**没有规则条纹**；
   黑白双色；橘猫要求鲜明橘占比 ≥ 0.15（否则按条纹判狸花）。

**判不出来就返回空 + 原因**，不会硬编颜色。

`/health` 的 `attrSource` 告诉你当前走哪条路：

```
"attrSource": "heuristic"   # 本地色域分析（没装 CLIP 时的正常值）
"attrSource": "clip"        # CLIP 在工作
"attrSource": "api"         # 配了 ATTR_API_URL 的远程接口
```

想看每张图具体判成了什么颜色、各色占比多少，用 `/v1/embed`（返回 `attrPalette`）。

## 八之三、夜间 / 远拍的照片：花色判错 + 候选一眼假（2026-10-26）

### 症状

用户上传夜间白猫实拍（猫站在远处台面上，占画面 5%）：

- 识别特征：品种「黑白奶牛猫」、毛色「奶牛」、花纹「黑白双色」—— 实际是灰白猫
- 匹配候选：「胖橘」**83%** —— 白猫怎么可能像橘猫

### 根因（两条独立，都用本地复现数据坐实）

**① 单色猫被明暗变化劈成「两色调」→ 误判奶牛猫**

奶牛猫的物理本质是两块不同色相的毛（V 分布**双峰**）。而一只灰白猫在光线下，
同一团毛会同时贡献 light（亮部）和 dark（暗部），两色调规则原封不动命中。
实测色域统计：

| 图 | white | black | gray | dgray | 原判定 |
| --- | --- | --- | --- | --- | --- |
| 标准白猫素材 | 0.135 | 0.110 | **0.453** | 0.332 | cow（错） |
| 用户夜间白猫 | 0.086 | 0.308 | **0.507** | 0.365 | cow（错） |

真奶牛照 gray 都在 0.2 上下 —— 所以把「gray 少」列为奶牛猫的必要条件即可分开。

**② 目标太小 → 查询向量不可信 → 候选谁都可上**

把同一只白猫按比例缩小做对照（白猫档案 vs 橘猫档案的余弦差）：

| 猫占画面 | 与白猫档案 | 与橘猫档案 | 差值 |
| --- | --- | --- | --- |
| 39.5% | 100.0% | 74.5% | **+25.5%** |
| 28.2% | 90.2% | 74.5% | +15.7% |
| 8.5% | 81.2% | 68.2% | +12.9% |
| 3.2% | 66.5% | 61.5% | +5.0% |
| 检测框退化 | ~40% | ~43% | **−2.4% ~ −3.2%（全线配错）** |
| **用户夜间实拍（4.9%）** | **61.5%** | **63.8%** | **−2.3%（配错）** |

注意最后一行的形状：**相似度方向都反了**，而两者都超过 `MIN_SIM=0.62`，
所以任何阈值都救不了 —— 阈值只能分开"高/低"，分不开"对/错"。

**不是"暗"的问题**（此结论**只对模拟压暗成立**，见八之五）：同一张图单纯压暗到
0.4 倍，差值仍有 +17.7%。小目标场景的敌人是**降噪涂抹 + 小目标放大 + 背景干扰**。
真实夜间照（点光源 + 色偏 + 相机降噪）是另一个分布，同日深夜的第二例实拍证明
**近拍大目标也会配错** → 低光单独设门（`QG_MIN_LIGHT_MEAN_V`）。

### 修法

**质量门控 `engine._quality`**（`QG_MIN_AREA_RATIO=0.06`）：
检测框占画面 < 6% → `qualityOk=false` → **不出候选、花色也弃权**。
理由：硬给一个错误候选比说"看不清"更糟 —— 用户会照着错候选点「就是这只猫」，
把错样本写进特征库，污染是永久的。

6% ≈ 猫身占画面短边 1/4。手机正常举拍（猫占 15%~50%）不会误伤，
只有"站在两三米外随手一拍"会被挡 —— 那种照片本来就认不出来。

**奶牛猫判定加 `gray < ATTR_COW_MAX_GRAY(0.35)` 必要条件**（`attrs._decide` 规则 3）。
修复后：标准白猫素材 cow → **gray**（灰白猫判灰猫，合理）；
夜间白猫 → 仍会走单色规则，但**会被质量门控拦下不展示**。

### 为什么不再往上调 MIN_SIM

`MIN_SIM=0.62` 已经是对的：夜间查询的相似度全挤在 0.62 附近（61.5% / 63.8%），
提高门槛只会让**所有**猫都出不了候选，包括本该匹配对的（白天查询 top1 典型 80%+）。
真正该做的是**在检索之前判断这张查询图可不可信**，而不是在检索结果里挑。

### 相关字段（`/v1/recognize` 的 `meta`）

| 字段 | 说明 |
| --- | --- |
| `qualityOk` | false = 查询图不达标，**候选为空是设计如此** |
| `qualityReason` | 给人看的原因（"猫在画面里只占 5%，距离太远…"） |
| `areaRatio` | 猫占画面的比例，用于核对门槛 |
| `lightMeanV` | 猫体平均亮度（低光门控输入），排查「夜里被拦」先看它 |
| `crop` | 实际用的检测框，排查"框是不是框偏了" |

## 八之四、标准素材判错花色：橘猫→三花、黑猫→狸花（2026-10-26）

与八之三同一批实测里发现的两条独立误判，都是**判定规则缺必要条件**，
不是阈值问题（调阈值会顾此失彼）。

### 症状

| 素材 | 误判 | 关键统计 |
| --- | --- | --- |
| 橘猫标准素材（浅橘/乳橘猫+白墙+阴影） | 三花 | orange 桶 0.003、brown 0.279、white 0.285、dark 0.31 |
| 黑猫标准素材（黑猫趴灰沙发） | 狸花 | stripe 0.63 过线、暖色系仅 6.8%、gray 0.637（沙发布纹） |

### 根因

**橘猫→三花**：宽松三花规则（规则 4：`white≥0.16 and dark≥0.12 and warm≥0.14`）
不看「有没有鲜明橘」。而「浅橘猫 + 白墙背景 + 阴影」的统计和三花**一模一样** ——
白来自墙、暗来自阴影、暖来自落进 brown 桶的低饱和橘毛（橘桶门槛 S≥105 且 V≥157，
乳橘毛 S≈70~105 够不着）。三者在 ratio 空间无法区分，必须在规则里加「真三花必有
可观鲜明橘块」这条存在性证据。

**黑猫→狸花**：狸花规则（规则 7：`has_tabby and dark≥0.12`）对「条纹分从哪来」
不作区分。黑猫趴在沙发/地毯上时，织物褶皱是强方向性周期纹理，stripe 照样过线
（实测 0.63）；而狸花的物理本质是「**暖色底毛** + 深色条纹」—— 底毛的色相/饱和度
对曝光免疫（S=(max−min)/max 是比值，H 是角度，只有 V 随亮度塌），这是夜里唯一
可靠的暖色证据。

### 修法（都在 `attrs._decide`，新配置见 `config.py`）

1. 规则 4 加 `orange >= ATTR_CALICO_MIN_ORANGE(0.05)`：没有鲜明橘的
   white+dark+warm 改走规则 5 判橘系（橘白猫）。代价：弱光下的真三花可能
   降级成橘系 —— 比「墙根下的橘猫被判三花」好得多。
2. 规则 7 加 `warmish >= ATTR_TABBY_MIN_WARM(0.10)`：`warmish` 是新统计量
   （`_stats_of`，H 5~55 且 S≥50 的像素占比，**不限亮度**）。低于门槛的高条纹分
   只能来自环境织物纹理。代价：灰狸花（蓝虎斑，底毛偏中性）会降级成 gray/tabby
   （颜色判灰、花纹仍标条纹）。
3. `warmish` 的**缺失语义是 None**：`_decide` 收到 None 就不设门槛（旧调用方
   行为不变）；`merge_stats` 只对提供了 warmish 的帧平均，一帧都没有就输出
   None —— 绝不能把「没算过」折算成 0（`test_disagreement_written_to_reason`
   实测踩中过）。

修复后：橘猫素材 → **橘猫**（两种取景）、黑猫素材 → **黑猫**（stripe 虚高也被
warmish 挡住）、白猫素材判定不变。回归测试：`test_attrs.py` 的
`TestCalicoLooseGate` / `TestTabbyWarmGate`。

### 排查入口

`tools/attr_probe.py`（`_stats_of` 现在会输出 warmish）；色桶落点、暖色像素的
S/V 分布这类中间量，参考八之三的诊断思路逐环打印。

## 八之五、夜间近拍：白猫判「黑猫」+ 候选 79.7% 配错（2026-10-26 深夜）

与八之三**同日第二例、不同根因**。这张猫占画面 47%（占比门控放行），
但结论照样全错 —— 证明「目标大」不等于「特征可信」。

### 症状

| 环节 | 实际输出 | 应该是 |
| --- | --- | --- |
| 花色 | **黑猫 / 纯黑 / 纯色，conf 0.824** | 白猫（或弃权） |
| 候选 | 胖橘 79.7%（线上） | 不该出候选 |

### 根因（本地逐环复现坐实）

**① 花色判黑 —— 曝光自适应的 p98 锚点在夜间被点光源打破。**
色桶的「白」是绝对亮度（V≥175±半幅 shift），而夜间白毛的 V 只有 92~184。
锚点假设「p98 反映环境光、与猫毛色基本无关」，但夜里画面最亮的恰恰是
**灯/反光**（实测 p98=242）而不是白毛 → shift 反而为正（+17.4），
w_hi 被抬到 183.7，白毛更进不了白桶。结果：
white 0.087 / gray 0.514（其中暗灰 dgray 0.375）/ black 0.303
→ `dark=0.678 ≥ 0.5` → 单色规则判「黑猫」。人眼看是白猫靠的是轮廓与
环境常识，纯像素统计在这种逆光夜景里**没有判白的依据**。

**② 检索方向反了 —— 真实夜间照的嵌入整体不可信。**
本地对照实验（白天素材建库：白猫/橘猫/灰猫/英短）：
夜间查询 → 白猫档案 **53.7%，排在英短 57.5% 后面（方向反了）**，
全部低于 MIN_SIM；gamma 0.45/0.55 亮度增强后再查询仍排第二，救不回来。
对照：白天白猫查询 → 白猫档案 93.8% 断崖第一。
⚠️ 八之三的旧结论「压暗 0.4 倍区分度仍有 +17.7%，所以不看亮度」只对
**模拟压暗**成立；真实夜间照（点光源 + 绿桌面色偏 + 相机降噪）是另一个分布。

### 修法：低光并入质量门控（`engine._quality` 第二维）

- 新配置 `QG_MIN_LIGHT_MEAN_V = 125`：检测框 crop 的平均亮度（HSV 的 V）
  低于它 → 与占比门控同后果：**不出候选、花色弃权**，前端走既有的
  「这张照片没法比对」卡（`qualityReason = "光线太暗…请靠近光源重拍"`）。
- 新增 `engine._box_light`：96×96 采样算框内平均 V，单次 <1ms；算不出
  （异常）返回 None → 门控不生效，绝不连累主流程。
- 实测分布：夜间 105 / 113，白天 8 张素材全部 ≥178 —— 两簇间隔 >50，
  阈值 125 取中，黄昏/室内灯（130~170）不受影响。
- ⚠️ 实现铁律：`light is not None` 显式判断，V=0.0 是合法值不能被真值判断吞掉。

为什么选择「拦下」而不是「修花色规则」：夜间逆光图里 dark=0.68 是**像素事实**，
任何规则把它改判成白都要靠「环境常识」，纯统计做不到；而错误花色会去硬过滤候选
（black×orange 剔除真橘档案）、错误候选会诱导用户点确认 —— 拦下并说清原因
是唯一不产生新伤害的选择。真实需求（夜里找猫）等后续有夜间建库数据再评估。

### 相关字段（`meta`）

| 字段 | 说明 |
| --- | --- |
| `lightMeanV` | 猫体平均亮度；夜间 105/113、白天 ≥178，一眼分簇 |
| `qualityOk/qualityReason` | 同八之三，低光时 reason 为「光线太暗…」 |

回归：`test_quality_gate.py` 的 `TestLowLightGate`（8 项：暗拦/亮过/None 不门控/

## 八之二、视频识别失败 / 「同一个素材被算了很多次」（2026-10-25）

### 症状

服务端日志里同一个视频（`videoUrl` 完全相同）在一分钟内被请求很多次，
每次都完整重跑一遍，前端最后显示**「识别服务暂时不可用」**：

```
/v1/recognize 3621ms（... 检测782ms 推理2388ms 帧3 候选0 库7）   ← 第 1 次
/v1/recognize 3577ms（... 检测813ms 推理2328ms 帧3 候选0 库7）   ← 第 2 次（同样的素材）
/v1/recognize 3544ms（... 检测809ms 推理2331ms 帧3 候选0 库7）   ← 第 3 次
...                                                              ← 共 10 次，全丢
```

### 根因：两条时间线对不上，不是「识别不准」

```
云函数 poll 路径能给 AI 的窗口   AI_POLL_CAP_MS = 1800ms
视频识别服务端实际耗时                            ≈ 3500ms
```

窗口是由**客户端 `callFunction` 约 3s 的硬预算**决定的，放大不了。
于是每一轮轮询必然超时：

```
poll#N  发起请求 → 服务端开始算（要 3.5s）
1.8s    云函数窗口到期，放弃这次调用
3.5s    服务端算完，但已经没人来取结果了 → 丢弃
4.4s    poll#N+1 又从头算一遍
```

循环到 `aiAttempts` 用尽 → 降级本地引擎 → 前端显示「识别服务暂时不可用」。
**服务端从头到尾是好的**（日志里检测框、花色、候选数都正常），
问题在于结果回不到客户端。

### 修法：第二次调用直接拿第一次的结果

窗口注定算不完，那就别让第二次重新算 —— 服务端加**结果缓存 + per-key 计算锁**
（`server/app/recocache.py`）：

| 轮次 | 行为 |
|---|---|
| poll#1 | 无缓存 → 自己算（3.5s）→ 云函数 1.8s 放弃，但服务端跑完并写入缓存 |
| poll#2 | 命中缓存 → 几十毫秒返回 → **成功** |

关键配套：

- **`waitMs`**（云函数随 AI 窗口下发）：让「前一次还在算」时后来者**排队等**，
  而不是各算各的。少了它，两倍的 CPU，且两个请求都在 1.8s 窗口内超时，永不收敛。
- **「排队中」按超时处理**：503 不能被记成明确失败
  （`FEAT_FALLBACK_ATTEMPTS` 只有 6 次，视频第二轮就会排队，
  记成明确错误会在拿到结果前就降级）。
- **失败不缓存**：一次网络抖动不能被记住整个 TTL 周期。

### ⚠️ 部署前提：最大实例数必须是 1

缓存是**进程内**的。多实例各缓存一份，命中率会退化回「每轮重算」。
这与 `INDEX_BACKEND=cos` 的约束相同，云托管控制台里把最大实例数锁成 1。

### 自查

- `GET /health` 的 `cached` / `computing`：缓存条数、正在计算的条数。
  识别很慢但 `cached` 恒为 0 → TTL 被关掉了，或者多实例部署。
- 响应 `meta.cached=true` → 本次命中缓存（视频第二轮就该是 true）。
- 日志里同一个素材出现多次**但只有一次是 `cached=false`** → 缓存正常工作；
  如果每次都是 `cached=false`，说明 key 变了（最常见：`waitMs`/`frames` 之外，
  `videoUrl` 里的临时链接签名每次不同 —— 换链逻辑被放到客户端就会这样）。

### 前端配合

视频必然走「同步超时 → 轮询接手」，进度条会在 92% 附近停十几秒。
所以文案里必须**先给预期**：开局「视频处理中，约需 10~20 秒…」，
轮询阶段「正在逐帧提取特征并比对…（视频约需 10~20 秒）」。
另：轮询前三轮间隔 1.2s（原 2s）—— 一条识别通常在前两三轮就出结果，
固定 2s 等于每次白加 2.4 秒。
